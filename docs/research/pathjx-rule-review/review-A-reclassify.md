## 标准本身的问题

1. **"本机"的字面陷阱**：PathJX 的"本机 CI""本机网页端到端"指"在本地跑、不走 GitHub Actions"。标准应写明：看条目是否只在某一台指定机器上成立，不看是否出现"本机"二字。
2. **"当前提交"的覆盖者范围**：run-spec 的脚本被 git 忽略，从 video-studio 的 tag 安装，哈希由 `skills-lock.json` 固定。它们算不算 a6c42b1 的"脚本或工具默认行为"，直接决定 C008–C018、C027、C028、C030、R012 的归类。建议写明：哈希被锁定的已安装技能算覆盖者，理由里要写 tag 和文件行号；没有锁定的不算。
3. **历史实测和证据没有归属**：C055、R039、R077、R093、R095 这类记录既不是规则，也不是坑。建议加一类"记录"（或明确归入仓库规则并标"记录"），同时要求它们放进日志或研究目录，不留在规则文档里。
4. **"用户"是决策者还是个人**：D036、D053、D056 是写给"用户"的，但这里的用户是产品负责人兼决策者。建议补一句：给决策者的书面决策材料（可读性、列出代为决定的事项）归仓库规则；聊天语言和详略归个人偏好。
5. **agent 的等待方式**：标准的个人偏好写的是"想多久被打扰一次"，没覆盖"没有用户参与时 agent 是阻塞等待还是轮询"（影响 token 成本）。建议明确：只关系到对用户的打扰频率和状态回复的，归个人偏好；影响资源消耗或调度的，归仓库规则。
6. **"最终答复"的双重身份**：对 Codex 来说，最终消息就是汇报产物。建议标准区分"写进仓库、issue 或汇报文件的书面产物"和"聊天回复"。
7. **部分覆盖的处理**：大多数句子是"能机械检查的部分＋语义部分"。建议允许按片段拆成"可删除＋仓库规则"（如 C028），同时要求每片单独读得懂，避免出现 A015/A016 那样的残句。
