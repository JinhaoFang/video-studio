# PathJX 规则归类的判定标准（第二版，2026-10-30）

第一版的错：把"重复验证习惯"列为个人偏好，看到"本机"二字就判本机说明，只看了 9 个文件。第二版吸收了复核 A 的七点和用户 10-30 的裁决。

## 判定问题

明天换一个人或另一台机器上的 agent 接手 PathJX，这条还必须成立吗？

## 五类

- **仓库规则**：严格的项目规范，以及防止项目变混乱的约束。约束产物、流程、验收、协作，不管是谁提出的、带不带日期或"用户"字样。包括：验证预算的原则和"什么时候不用重跑"、两条线如何协作、所有人做安排都要知道的拓扑事实（例如 GPU 在哪台机器）、账号层面的限制（例如 GitHub Actions 暂停改用本机 CI）、权限决定、agent 没有用户参与时阻塞还是轮询（影响资源消耗）、写给决策者的书面材料要求（可读性、列出代为决定的事项）。
- **现场参数**：会随现场调整的数值和开关：并发名额、磁盘余量、超时、预算秒数、worker 数。只放一处（配置文件，或一份文档里的一节），规则只写原则并引用这一处，不复述数值。
- **本机说明**：只在某一台指定机器上成立、修法也只对那台机器有意义的坑：工具装在哪、绝对路径、下载失败的绕法、PATH 顺序。看条目是否只在某台机器上成立，不看有没有"本机"二字："本机 CI""本机网页端到端"指不走 GitHub Actions，两台机器都适用。放进开发环境文档里按机器分的一节。
- **个人偏好**：只关系到某个人和 agent 怎么对话：聊天语言、聊天里讲多细、会话长度、多久打扰一次。写进那个人的用户级配置。写进仓库、issue、汇报文件的书面产物不算聊天，按仓库规则判：对 Codex 来说最终消息就是汇报。
- **记录**：历史实测、证据、当时为什么这样定。不是规则也不是坑，放进日志、研究目录或 ADR，规则文档里最多留一句指针。

**可删除**：已有覆盖者完整覆盖时删掉文字。覆盖者是当前提交里的脚本、检查、工具默认行为，以及哈希被 `skills-lock.json` 锁定的已安装技能（理由写 tag 和文件行号）。只覆盖一部分的不算；可以把一句拆成"可删除＋仓库规则"两片，但每片单独读得懂。

## 两条线

"线"按领域定义：产品工程线、算法与数据线，管谁负责什么。机器只说在哪跑，单独写环境说明。算法线机器上做产品线的工单是正常情况。两条线共用的部分只写一处，每条线的文档只写本线独有的。

## 用户 10-30 的裁决

| 事项 | 结论 | 类 |
|---|---|---|
| 锁定测试集 | 按 10-25 放宽后的规则，不限制死：冻结后可以多次打分，每次登记。放宽的原因是只跑一次太死，没有其他数据，测试后无法继续调优 | 仓库规则，记成 ADR 0002 |
| 临床措辞 | 设计负责人出方案，用户最终决定 | 仓库规则 |
| 甲状腺对外说法 | 统一为"跨院适配"，包括演示材料的屏幕文字 | 仓库规则 |
| Codex 并发名额 | 两台机器统一 3 个，写进执行配置 | 现场参数 |
| 演示运行时跑完整检查 | 可以 | 仓库规则 |
| 原始数据写权限 | 只读是规则；需要写入时由设计负责人在派发前打开、验收后关回，Codex 不改权限 | 仓库规则 |
| 磁盘余量 | 规则只写"开跑前检查余量，不够就停下报告"，数值放资产文档一处 | 仓库规则＋现场参数 |
| 长时间运行的进程 | 要跑很久或要排队等资源的进程，脱离 Codex 会话启动，日志写文件，汇报写进程号和日志位置 | 仓库规则 |
| 院方演示日期 | 第一阶段 10-28；第二阶段未定 | 记录 |
