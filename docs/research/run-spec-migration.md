## 碰到的问题

每条都写了初始化技能可以怎么处理。

1. **仓库属主不对**：目标仓库的文件属于 root 和另一个用户，jh1 用 `git`、`gh` 都报 dubious ownership。用户修好后才能操作。这和本仓库建仓时的第一个问题一样。→ 探查环境时第一项就查，不能用时停下来告诉用户。
2. **依赖装在别的用户名下**：测试要用的 Playwright 浏览器装在 root 名下，jh1 跑测试有 146 个失败。补装以后全部通过。Codex 也以 jh1 身份运行，同样受影响。→ 探查环境时，用派发 Codex 的那个用户实际跑一遍验证命令，不只看配置。
3. **测试只在 CI 上间歇性失败**：回归测试偶发"体系总览页有 4 个错误"；本机连跑三遍都通过，只改文档的提交在 CI 上也会失败。`land` 合并前要跑验证，不稳定的测试会让合并随机失败。→ 探查环境时查最近几次 CI 的结果；有不稳定的测试，列为彩排 spec 的第一项。
4. **集成分支的名字对不上**：`run-spec` 按 `spec/<号>-` 找集成分支，目标仓库用的是 `integration/phase-0`。办法是先合回 `main` 作为检查点，之后从 `main` 新开。→ 检测已有的长期分支，建议先建检查点。
5. **`.gitignore` 带斜杠的规则匹配不到软链接**：目标仓库原来写的是 `references/`、`.cache/`。worktree 里这些目录是软链接，带斜杠的规则管不到，worktree 会不干净，`land` 会拒绝合并。迁移包的片段本来就不带斜杠，但没写原因，目标仓库已有的规则不会自动改。→ 自检时用 `git check-ignore` 实测一个同名软链接。
6. **第三方技能已经进了 git**：要用 `git rm -r --cached` 退出跟踪。这种提交不能按 `AGENTS.md` 的写法 `git commit … -- <路径>` 提交：只提交指定路径时，git 会按工作区的现状提交，而文件还在磁盘上。改用"核对暂存区后不带路径提交"。→ 初始化技能里写明这一步。
7. **产品技能和软链接冲突**：目标仓库的方案规定，本库将来的产品技能也放在 `.agents/skills/` 并进 git；`run-spec` 却把整个 `.agents` 软链接进 worktree。两者不能同时成立，已记进那边路线图的待定项。→ `symlinkDirectories` 的粒度只到目录，初始化技能要问清 `.agents/skills/` 里会不会有自己的技能。
8. **用户本地改过第三方技能**：目标仓库里 `to-spec`、`implement-spec` 被改成了可由模型调用，没有提交。`.agents/skills/` 下的技能 Codex 都能看到，这类改动会扩大 Codex 能自己调用的范围。→ 迁移前用 `git status` 和锁文件里的哈希查第三方技能有没有本地改动，有就问用户。
9. **原有的 `AGENTS.md` 结构不同**：要把命令手册这类内容移出去，再按 `dual-role-workflow` 加上角色一节；setup 生成的「Agent skills」一节要原样保留。→ 这一步要判断，留在对话里做，初始化技能只检查结果有没有角色一节和提交格式。
10. **产品里也有"角色"和"用户"**：目标仓库的术语里有需求方、裁判、agent，和开发协作的设计负责人、工程负责人是两套东西；术语表还规定产品里避开"用户"一词，而规则文档里"用户"指和 agent 对话的人。在 `AGENTS.md` 角色一节写明了对应关系：规则文档里的用户是项目发起人，在产品里同时是需求方和裁判；方案里的 agent 指使用本库的 Claude Code 和 Codex。→ 对齐时要问。
11. **护栏不能原样带过去**：本仓库的文档命令护栏内置 pnpm 10 的命令表，目标仓库用 pnpm 12。→ 回答路线图里"仓库级护栏要不要随行"时考虑这一点：护栏按目标仓库的工具链重写，作为那边彩排 spec 的候选，不直接复制。

12. **没读完目标仓库的设计文档就改了规则**：第一版迁移只读了方案的目录和第 7～8 节，有两处和已定的决定冲突。一是把"按定稿实现排法"划给了工程负责人，而方案第 3.6 节规定几何归体系管，spec #1 写明体系好不好由裁判人工验收、检查器零错误只是必要条件；已改为体系本身归设计负责人，工程负责人接做体系时暴露的工具缺口。二是把命令手册移出了 `AGENTS.md`，而 spec #1 的用户故事 63 要求它写在那里；保留了移出，靠 `AGENTS.md` 的指针做到"不必从代码推断用法"，已告知用户。→ 第 1 步读完方案、术语表、ADR、进行中 spec 的全文。
13. **改了目标仓库已有的命名，没先问**：方案文件名是中文且带空格，迁移时改成了 `docs/plan.md`。用户要求改回原名。→ 已有的命名和结构要改，先问人。
14. **动手前没把迁移的步骤讲给人听**：用户说了"全权负责"以后，设计负责人直接执行，用户只看到结果，事后问"迁移到底如何进行"。→ 动手前先讲要走的步骤，人确认后再开始。

没有成为问题的：

- Codex 的项目信任配置里没有目标仓库，派发照样能跑。
- 目标仓库的 `references/` 里已经有 DispatchDock v0.1.3，直接用它的安装器。
- Node 版本要求（22.18 以上）两边一致，工单脚本不用改。

### 经受住了检验的

- **`run-spec` 原样复制就能用**：技能和工单脚本一行没改，只写了 `run-spec.json` 和 `run-spec.md`，`frontier`、`link`、`dispatch`、`land`、`accept`、`cleanup` 和按批审查都跑通了。

### 问题

接着上面的编号。

15. **交接提示词里的命令没实测**：本仓库的设计负责人在交接提示词里，把实测过的"按技能名逐个恢复"简化成"恢复整个技能目录"，没再测；对齐会话原样写进工单。执行会话动手前在临时 worktree 里实测，发现会删掉进 git 的 `run-spec`、带回已移除的旧技能，改成按 `skills-lock.json` 逐个恢复。→ 交给下一个会话的命令，交实测过的原文。
16. **环境前提是推测**：对齐会话把"CI 机器 4 核"当事实写进 spec，私有仓库的 GitHub runner 实际只有 2 核。Codex 按 4 核在本机试了约 6 分钟复现不出来，按工单预留的退路改到 CI 上诊断才查清。→ 写进 spec 的环境事实先测（例如在 CI 上打印一次核数）；测不了的标明是推测，并给退路。15、16 两处都靠工单里要求实测的验收项和预留的退路拦住。
17. **对齐时技术性的取舍没讲白**：第一轮问题里，"不稳定测试怎么算修好"附了三种做法和 Actions 时长，用户按推荐通过后又问"CI 这里不理解"。补讲现状时，设计负责人自己发现原来的标准（CI 连跑 10 次）证明不了修好，改成先在本机复现再修。→ 要人拍板的问题涉及技术现状时，先用白话讲现状再问。
18. **派发指令写死"不要推送"**：有的验收要 CI 运行链接，而 CI 只在推送后运行。这次在补充说明里临时放开。→ 工单能声明允许推送自己的工单分支。
19. **`land` 在 rebase 后不重装依赖**：#37 新增了依赖，后合并的 #38 验证必然失败，设计负责人手动在 worktree 里重装。→ rebase 改动了锁文件时，先运行安装命令。
20. **远端分支没人删**：推送过的远端工单分支，`cleanup` 不删；`cleanup` 在 PR 合并之前运行，集成分支合并后也没人删。两个仓库原来都没开 GitHub 的"合并后自动删除分支"，已打开，并补进开局清单。→ `cleanup` 删除远端工单分支。
21. **最后一批的审查和收尾审查重合**：执行会话自行合并成一次。→ 写进 `run-spec` 第 6 步。
22. **审查的用量没有记录**：工单派发的用时和 token 由 `accept` 自动写进验收评论，审查的没有。写汇报时要去 `~/.codex/sessions/` 翻，还要自己加上审查开的子代理。→ 审查结论的评论自动附上用量。
23. **派发时做的决定只在本机**：派发 #38 时，"`node` 后的路径按是否进 git 判断"这个决定写在补充说明文件里，返工单 #39 修的就是它漏掉的另一半（文件还要实际存在）。`cleanup` 以后，这个决定只留在汇报里。→ 派发时临时做的决定，同时评论到工单上。
24. **验证步骤在 4 份文档里各列一遍**：`AGENTS.md`、命令手册、工作流总图、`run-spec.md` 都写了 `pnpm verify` 有哪几步。三张并行工单各加一步，每张都改这几份文档，最后合并的一张在 6 个文件上冲突，其中 3 个是文档。这个写法是从本仓库带过去的，本仓库的 `AGENTS.md` 也一样。→ 步骤只在步骤表和命令手册里列，其他文档写指针。

## 真实使用：spec #1 第 0 阶段

彩排以后，design-system 用安装版的 `run-spec` 跑完了真实的 spec #1（2026-10-12 22:11～10-13 16:25），用户审 PR #55 后又在另一个会话里返工（10-13 18:04～21:50），PR 已合并。证据来自两次会话的记录（`~/.claude/projects/-root-project-design-system/` 下的 `7f9795da…`、`3818ba85…`）、那边的汇报 `docs/reports/spec-1-phase-0.html` 和 git 历史。

### 经受住了检验的

- **工单脚本**：两次会话里 `dispatch`、`land`、`accept`、`link`、`review`、`cleanup` 反复使用，都跑通。`land` 两次停在 rebase 冲突，按提示解决后重跑即可；一次验证失败暴露了两张工单叠加才出现的问题，退回返工。
- **按批审查**：三次审查共发现 12 条，其中 4 条是设计负责人自己做的部分违反了自己写的规则。
- **定稿先行**：返工时设计负责人先做可操作的原型和规则说明，Codex 照着实现，三轮后通过，用户点名肯定。
- **先给用户看方向**：返工时孔版印刷的样张内容先交用户确认，一次通过，成品是用户评价最高的一件。

### 问题

接着上面的编号。

25. **`role:design` 的工作交给了子代理**：12 张体系工单迁移时没有执行角色，执行时一次全标成 `role:design`。量太大，设计负责人自己建 worktree，开了 4 个 Claude 子代理去做（每个的任务通知报 32～39 万 token），4 次撞上额度上限、2 次卡住，约 5 小时停摆；用户两次问"为什么是你在写代码"。规则其实写了：角色文档开头写着"量大、能写清楚的执行交给工程负责人"，`dual-role-workflow` 的描述写着"把大部分 token 花在 Codex 上"，`run-spec` 写着"在主工作区自己做"。但同一份角色文档的分工清单把整套体系都列进"自己做"，清单比原则具体，agent 照清单做；"自己做"没说子代理算不算，全局规则又允许自行委派。→ `run-spec` 第 3 步写明 `role:design` 在主会话亲手做、一次一张，量大就把方向写进工单派出去，子代理只准备供判断的材料；`setup-run-spec` 核对分工按决定和体量分、清单和原则说法一致；迁移时和用户一起给进行中的工单定执行角色。
26. **难回头的方向没给用户看**：用户授权设计负责人代行裁判验收后，两套新体系的方向由设计负责人从方向稿里自己挑，三套体系共用一份内容。用户到 PR 才看到：6 条意见、9 张返工单，一套体系整个移除。→ `run-spec` 写明难回头的方向决定在实现前给用户看，代行只管成品。
27. **写了的规则没被读到**：生图规则在迁移时就写进了那边的 `docs/workflow/README.md`，执行会话直到收尾更新路线图才第一次打开这份文档。角色文档指向它的两句话，一句是"整体流程见…"，一句讲交给裁判的预览，都不会在做图像时被想起。孔版第一版由 Codex 用代码画人物和望远镜，Codex 没有生图接口，验收两轮也没挑出来。→ `run-spec` 第 3 步要求开工前按角色文档的指针读这类工作的规则；`setup-run-spec` 核对指针按触发条件写。
28. **教训只进了本机记忆**：用户在返工会话里讲的工作方式（定稿先行、样张内容先确认），设计负责人写进了 Claude 的本机记忆，规则文档里没有。Codex 和别的机器上的会话都看不到。→ `run-spec` 写明执行中的工作方式反馈写进规则文档或路线图待定项。
29. **参考文档难读、易冲突**：那边的命令手册 54 行，最长一行 1,971 字，spec #1 期间 18 次提交改它。派发补充说明反复写"只加自己那一项"，两次 `land` 冲突都在它身上。→ `setup-run-spec` 建议按需读的参考文档一条事实一行、按主题分节；那边的命令手册在 design-system 的改进里拆。
30. **没有"PR 审查后返工"这条路**：`run-spec` 写到开 PR、交汇报就结束了。返工会话即兴处理得对（返工单挂原 spec、同一集成分支、审返工范围、更新 PR 正文），但汇报里的 KPI 是手算的、时间线坐标写死，补数据时数错、画出了框。→ `run-spec` 第 7 步补上返工的做法；`report.md` 要求数字和坐标从数据数组算。
