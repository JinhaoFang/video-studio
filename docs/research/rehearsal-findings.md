# 彩排发现：Matt 技能与 DispatchDock 的结合

彩排（spec #1"工作室护栏与验收工具"，2026-10-11）的目的之一，是检验 Matt 的技能和 DispatchDock 的技能结合起来的流程，找出问题、优化流程，以后迁移到其他配备这两套技能的仓库。下面是彩排中得到的真实经验，供 spec #1 完成后的复盘使用。每条标明状态：**已定**（用户已决定，复盘时落实）、**待判断**（等用户决定）、**已落实**（spec #1 里已经改了）。

## 已定，复盘时落实

1. **审查按"一批"做，交给 Codex 执行。** 一批并行的工单合并后审一次，spec 收尾再审一次；审查由 Codex 跑，不再由设计负责人开子代理。依据：
   - 这次设计负责人用 `code-review` 跑了 12 次子代理审查，每次 5 万到 14 万 token，全花在 Claude 这边，和"把大部分 token 花在 Codex 上"的分工初衷相反。
   - 逐张审查拦住了 #5、#6 的真问题（eslint 改动的副作用、合并提交的判断能被绕过）；收尾的统一审查发现的主要是跨工单的问题（qa 四个子命令各写一套公共代码），逐张审查看不出来。两种都有用。
   - 复盘要定：Codex 怎么跑两条线（它能加载 `code-review` 技能）、"一批"的边界、审查发现的问题怎么回到工单。
2. **spec 完成后，设计负责人向用户做一次可视化的工作汇报，然后清理中间产物。** 汇报是向用户汇报工作，不是让用户检查中间产物：说明这次的任务是什么、做成了什么、关键决定、遇到的问题和处理、遗留。确实值得汇报的细节可以放进去（比如一张关键的验收图），git log、`.codex-runs/` 日志这类不放。汇报后，清理本 spec 在 `.codex-runs/` 和 `out/qa/` 里的中间产物，不然后续任务会越积越多。复盘要定：汇报的形式和生成方式、清理的范围。
3. **spec 和工单不写文件路径**，由执行的 agent 自己查看和决定。复盘要定：本仓库工单约定里的"写入范围"（现在写到目录一级）怎么调整。
4. **两套标签都保留**：Matt 的分诊标签（`ready-for-agent` 等）和本仓库的执行角色标签（`role:*`）。
5. **并行派发做成脚本。** 现在每开一个 worktree 都要手工建软链接（`references/`、`.agents/`）、装依赖、用派发脚本的绝对路径派发，事后手工 rebase、快进合并、归档记录、删除 worktree。这些步骤是固定的，做成工单脚本的子命令。
6. **spec 正文随拆单更新。** 这次 spec 里写的是"8 张工单"，`/to-tickets` 实际拆成 10 张，后来又加了一张返工。拆单之后要同步 spec，或者 spec 里干脆不写工单清单，只指向它的 sub-issue。
7. **融合层改用通用的名字，并抽出仓库特有的部分。** 现在把两套技能接起来的主要是 `studio-tickets`，此外还有 `docs/agents/issue-tracker.md` 的工单约定、`docs/workflow/README.md` 的阶段对照、`docs/roles/` 的两份角色文档、`AGENTS.md` 的"角色"和"技能"两节。这套要迁移到其他仓库，所以：
   - `studio-tickets` 要换一个不带本仓库色彩的名字。
   - 里面写死的本仓库内容（主工作区的绝对路径、`pnpm verify`、要软链接的目录清单）挪到仓库自己的配置或文档里，技能只保留通用的步骤。
   - 复盘时把上面这些融合点逐个分成"通用"和"本仓库特有"两类。

8. **有价值的工单过程留在对应的 GitHub issue 里。** 本地的 `.codex-runs/`、`out/qa/` 会被清理，GitHub 上的内容能长期保存，也能远程查看。验收评论已经承担了一部分（验证了什么、推断怎么处理）；值得留下的还有：派发的用时和 token、关键的实测数据、返工的原因。这些先进 issue，清理本地时就不会丢，写汇报时也从 issue 取数据。
9. **汇报保存在仓库里**（例如 `docs/reports/`），用户明确要求时才发布到 claude.ai。
10. **汇报的内容按下面的规范取舍。** 这不是死规定，每次的情况不同，由设计负责人判断：
    - **要有**：
      - 任务（目标、范围、一句话结果，含 PR 和 CI 的状态）
      - 交付了什么、对用户意味着什么
      - 关键节点的时间线
      - 成本与效率：派发次数、每次和合计的 agent 执行时间、token 用量（Codex 的输入和输出，以及设计负责人侧子代理的用量）、并行度、返工次数。数据缺失时写明原因
      - 质量：测试数、CI、关键的实测数据、审查发现了多少、怎么处理的
      - 谁做了哪些决定
      - 问题与处理，包括设计负责人自己的失误
      - 流程发现、遗留与下一步
    - **不放**：原始日志、git log、diff、评论全文。需要时给 issue 或 PR 的链接。
    - **细节**：只在影响判断时才放，比如一次异常长的派发、一次返工的原因。
    - **时机**：先汇报、后清理。成本数据要在清理 `.codex-runs/` 之前取出来，或者已经写进 issue。
    - 第一份按这个规范写的汇报：`docs/reports/spec-1-guardrails.md`。

## 待判断

11. **改了规则文档里提到的命令或约定的工单，文档要紧跟着同步。** Codex 每次派发都先读 `AGENTS.md` 和角色文档。#2 删掉了 `pnpm lint`，文档里却还写着它，这时再派发工单，Codex 会照着去跑一个不存在的命令。这次是临时插了一张设计工单 #3 补文档，其余工单都排在它后面。可选做法：拆单时让这类工单后面紧跟一张同步文档的工单，或者允许工程工单顺手改文档里对应的那一行。

## 已落实（spec #1 里）

- **worktree 并行派发**：从 #7 起采用，最多三路同时跑，没有互相干扰；做法写进了 `studio-tickets` 第 4、5 步（复盘时按第 5 条改成脚本）。
- **审查改到 spec 收尾统一做**：从 #7 起采用（复盘时按第 1 条改成"一批"、由 Codex 执行）。
- **删除 worktree 前先把 `.codex-runs/` 复制回主工作区**：#7～#9 的派发记录和验收图，就是因为直接删了 worktree 而丢失的。
- **两个待核实项**：`code-review` 重名、gh 2.83 建 sub-issue，结论写进了 `docs/roadmap.md`。

## 其他观察

- **进度汇报要写明 spec 还剩哪几步。** 十张工单关闭后，用户以为 spec 已经完成，其实还有收尾审查的返工和 PR。
- **验收产物的目录由 Codex 自己起名**（`out/qa/issue-5/`、`out/qa/ticket-8/`），清理时没法按 spec 归集。可以约定为 `out/qa/<spec>/<工单>/`，和第 2 条一起定。
- **`link` 真正执行时会打印整段 issue JSON**：GitHub API 的 POST 响应被原样输出，几百行，淹没了有用的信息。复盘时改成只打印一行结果。
- **被中断的调用可能已经执行了**：用户中断了一次"建工单并挂到 spec 下"的调用，设计负责人以为它没执行，重做了一遍，结果多出一张内容相同的工单（#13，已摘掉并关闭）。重做之前要先查一下实际状态。
- **合并方式**：PR #14 是 squash 合并的，`main` 上只剩一个提交。它的标题不符合提交格式（没有类型、没有 `Role`），17 个提交各自的 `Refs: #号` 在 `main` 的历史里也没有了。在 GitHub 网页上合并，本地钩子和 CI 都管不到；而「以后拆分」一节正是靠 `Refs` 来改写 issue 链接的。复盘时要定合并方式（merge commit、squash 还是 rebase），以及用 squash 时提交信息怎么写。
- **用时和规模**：从第一次派发到最后一张工单关闭约 1.5 小时。每次派发 6～10 分钟。Codex 每次的输入 70 万到 160 万 token（大部分是缓存），输出 1.1 万到 1.7 万。返工两次（#5、#6），每次都是一轮就修好。三路并行时，唯一的冲突是两张工单都往 `tools/qa.ts` 里登记子命令，两边都保留就解决了。
