# NASA 朋克（设计风格小课 04）：制作流程拆解

拆解对象：`references/震惊瘫坐！Opus 5.5 做的设计科普04…/`（B 站，频道"路北路陈"，5 分 54 秒）。
证据来源：视频简介 `description.md`、DispatchDock 仓库 `references/DispatchDock/`、对视频的抽帧、音频测量和旁白转写。
同目录还有：`shots.md`（逐章镜头表）、`style.md`（视觉与声音系统）、`transcript.md`（旁白逐句时间轴）。
标记约定：**【事实】** 有原文出处；**【推断】** 由画面、测量或 DispatchDock 文档推出，作者没有明说。

## 1. 一句话结论

一个人 + 两个 AI，**全靠文档协作**：Claude Opus 5.5 当"设计负责人"（选题、台本、分镜、风格、全部动画代码），Codex（GPT-6 Astra）当"工程负责人"（渲染管线、配音、对齐、配乐音效、混音、搜图），人只定方向、拍板和试听。
派活和验收用的是同一作者开源的 DispatchDock：Opus 写任务说明 → `codex-dispatch` 派给 Codex 后台执行 → Codex 提交并写汇报 → Opus 看汇报和渲染产物验收。

## 2. 分工（谁做了什么）

| 角色 | 担任者 | 本期负责的事 | 依据 |
|---|---|---|---|
| 人 | 作者 | 定方向、拍板、试听把关 | 【事实】简介"这期视频是怎么做出来的" |
| 设计负责人 | Claude Opus 5.5（Claude 桌面端的 Code 页） | 选题调研、台本与事实核对、分镜、画面风格、**所有动画镜头的代码**、画面字幕设计、封面、标题、简介 | 【事实】简介 |
| 工程负责人 | GPT-6 Astra（Codex CLI） | 渲染管线、旁白逐行对齐、配乐与音效的程序合成与混音、案例搜集；在 MiniMax 网页上逐段合成配音 | 【事实】简介 |
| 配音引擎 | MiniMax Audio `speech-2.8-hd` | AI 旁白 | 【事实】简介 |

为什么动画代码由"设计负责人"自己写、而不是派给 Codex：
dual-role-workflow 的判断标准是"**描述是否明显比实现短，结果能否客观验收**"。动画手感、构图、节奏属于"审美还在摸索、要边看边调的表现层"，写成能照做的说明本质上已经是在写代码，所以设计负责人自己写；能客观验收的（管线、对齐、混音、搜图）才派出去。【事实】`references/DispatchDock/skills/dual-role-workflow/SKILL.md`「分工」一节。

## 3. 协作机制（DispatchDock）

### 3.1 文档结构

dual-role-workflow 的 `setup` 会在项目里建这几样东西（DispatchDock 自己的仓库就是这样建的，可以直接当样例看）：

| 文件 | 作用 | 样例 |
|---|---|---|
| `AGENTS.md` | 共同规则：项目介绍、角色表、提交规则、文件归属、文档地图。多数 agent 工具都会读它 | `references/DispatchDock/AGENTS.md` |
| `docs/roles/design.md` | 设计负责人的职责、自己动手的范围、验收手段 | `references/DispatchDock/docs/roles/design.md` |
| `docs/roles/engineering.md` | 工程负责人的硬规则、完成标准、**汇报格式** | `references/DispatchDock/docs/roles/engineering.md` |
| `docs/design.md` | 设计文档（风格、已定 / 待定，带拍板日期） | `references/DispatchDock/docs/design.md` |
| `docs/specs/NNN-简述.md` | 任务说明，一次一个 | 公开仓库里没有附带 |
| `.codex-runs/` | 每个任务的汇报、精简进度、原始日志（不进 git） | 协议见 `docs/protocol.md` 第 3 节 |

关键原则：**角色写在文档里，不写在"你是哪个模型"里**。开工时告诉对方"你的角色是 X"，对方去读 `docs/roles/X.md`。

### 3.2 一次派活的完整回路

1. 设计负责人写任务说明：目标、范围、允许改动的文件、不做什么、参数与参照、验收标准（含要产出的验收产物）、汇报要回答的问题。
2. 先 `git commit` 任务说明，让 Codex 从干净基线开始。
3. 后台派发：`node <技能目录>/codex-task.mjs docs/specs/NNN-xxx.md --role engineering`。脚本把"角色 + 先读 AGENTS.md + 读角色文档 + 完成任务说明"拼成提示词，调用 `codex exec --json -C <仓库> -s <沙箱> -o <汇报文件> -`。【事实】`skills/codex-dispatch/lib/options.mjs`、`adapters/codex.mjs`
4. 等待期间不碰 Codex 可能在改的文件。
5. Codex 完成 → 只 `git add` 具体文件、提交（`[工程]` 前缀）→ 写汇报。
6. 设计负责人验收：先看汇报里的 **TODO(design)** 和 **推断清单**，对照验收产物（截图、关键帧、渲染短片）逐条确认，再抽查关键 diff，不逐行读代码。
7. 不满意的推断或 TODO 写进下一份任务说明，或者自己做最后的审美微调。

工程汇报的固定格式（9 项）：完成了什么 / 改动的文件 / TODO(design) 清单 / 推断清单 / 实现时核实的结论与证据 / 协议修改建议 / SKILL.md 需同步处 / 偏离说明 / 已知问题。
其中"推断清单"专门用来暴露工程负责人**没意识到自己在做的审美决定**（"调色板里有这个颜色就用了"、"放不下就缩小字号"）。【事实】dual-role-workflow `setup` 第 3 条。

### 3.3 在本机能不能用

- DispatchDock v0.1 官方只支持 Windows；派发脚本本身没有写死 Windows，只有"弹出只读进度窗口"是 Windows 专用。
- 本机实测（2026-10-11）：Linux + Node 22.23 下 `CODEX_DRY_RUN=1` 空跑正常，能打印记录名和将发给 Codex 的指令。官方要求 Node 24，真实派发还没验证。
- 本机已装 `codex-cli 0.161.0`，`~/.codex/auth.json` 存在（是否有效未验证）。

## 4. 制作阶段（按依赖顺序）

简介只给了"谁做了什么"，没给顺序。下面的顺序按依赖关系推出：配音是时间基准，画面和字幕都挂在它上面。【推断】

| # | 阶段 | 负责 | 产物 | 依据 / 说明 |
|---|---|---|---|---|
| 0 | 系列定位 | 人 + 设计 | 系列名"设计风格小课"、固定结尾"风格卡 + 给 AI 的描述" | 【事实】简介；画面里第 1 期瑞士风格、第 2 期卡带未来主义被回调引用 |
| 1 | 选题调研、事实核对 | 设计 | 带出处的资料：1975 年规范手册（NHB 1430.2）、1992 年废除、2015 年众筹复刻、2020 年 Demo-2、GQ 对 Istvan Pely 的访谈、Tahir Tanis 的 ArtStation | 【事实】简介"制作说明"；简介还专门声明"ARC Raiders 是分支"是观点不是事实 |
| 2 | 台本 | 设计 | 12 个章节、短句化的旁白稿（一句一条字幕） | 【事实】章节表；【测】191 句、平均 1.5 秒一句；【推断】句子短到一行字幕放得下，是为 TTS 和字幕同时设计的 |
| 3 | 分镜、画面风格 | 设计 | 镜头表、视觉系统（见 `style.md`） | 【事实】简介 |
| 4 | 配音 | 工程（Codex 操作 MiniMax 网页）+ 人试听 | 逐段的旁白音频 | 【事实】"在 MiniMax 网页上逐段合成了配音"；【推断】没用 API，而是让 Codex 用浏览器操作网页 |
| 5 | 旁白逐行对齐 | 工程 | 每行旁白的起止时间（驱动字幕和动画时间） | 【事实】简介；【推断】产物是一份时间轴数据 |
| 6 | 案例搜集 | 工程 | NASA 公有领域照片与手册扫描、游戏官方截图，带出处 | 【事实】简介；画面右下角都有 `IMAGE: …` 出处行 |
| 7 | 动画镜头 | 设计 | 每个镜头的代码 | 【事实】"所有动画镜头的代码" |
| 8 | 渲染管线 | 工程 | 代码 → 逐帧渲染 → 视频 | 【事实】"画面全部用代码逐帧生成"；用的是 Remotion 还是自建（如浏览器截帧 + FFmpeg）**无从判断** |
| 9 | 配乐、音效、混音 | 工程 | 程序合成的 BGM 与 SFX，整片混音 | 【事实】"配乐与音效为程序合成"；实测整片 -16.0 LUFS、LRA 2.9 LU（见 `style.md`） |
| 10 | 封面、标题、简介 | 设计 | 含章节、风格卡、可复制给 AI 的提示词 | 【事实】简介 |

验收手段（dual-role-workflow 要求每个项目都有）：渲染出的关键帧、短片、截图，设计负责人直接用 Read 看图。【事实】SKILL.md「作为设计负责人干活」第 5 条。对视频项目来说，第一批任务就应该让 Codex 把"抽关键帧 / 拼对比图 / 测响度"这类验收工具搭起来。

## 5. 从这期能学到的做法

1. **配音先行，时间轴以配音为准**。字幕按行切，动画的进场点挂在行的时间上，改稿就重配那一行再重新对齐。
2. **真实素材 + 代码叠层**：照片、截图、手册扫描是底，代码画的是 HUD 框、标签、彩条、批注、计数器、纸片——"讲解"信息全在叠层上，底图只负责"真"。
3. **一套视觉系统贯穿全片**：同一种字幕条、同一种标签字体、同一道彩条，章节内用"RULE 01…04"、"LAYER 01…07"这样的编号做结构。
4. **出处写在画面上，观点和事实分开写**：每张引用图都有出处行；有争议的判断在简介里声明是"我们的看法"。
5. **结尾给可复用的东西**：风格卡 + 能直接复制给 AI 的提示词，让一期视频变成"风格词汇表"的一页。
6. **贵的模型只做判断**：调研、写稿、风格、动画手感给 Opus；量大、能客观验收的执行给 Codex。
