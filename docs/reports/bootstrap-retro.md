# 建仓过程复盘

从 2026-10-11 16:18 用 `npx create-video` 建仓，到 19:38 把彩排交给新会话为止：人和 agent 是怎样一起把这个仓库搭起来的，哪些做法起了作用，哪些付了代价，建仓时的安排后来经受了怎样的检验。可复用的开局做法整理在 `docs/workflow/bootstrap.md`。

写于 2026-10-12，设计负责人。时间都是本地时间（UTC+8）。可视化版本见 `bootstrap-retro.html`，内容以本文为准。

## 要点

- **结果**：3 小时 20 分钟（16:18～19:38），从 Remotion 空模板到一个有规则、有分工、接好 GitHub、装好并冒烟测试过 DispatchDock 的私有仓库，共 8 个提交，外加 6 份参考视频拆解文档。之后的彩排（spec #1）和 spec #17 都直接在这个基础上开工。
- **时间分配**：会话 1 持续 2 小时 48 分钟，其中 agent 实际工作约 53 分钟，其余约 1 小时 55 分钟是用户在两次回复之间的时间。这段时间用户主要在会话外动手：修权限、换 pnpm、增删技能、跑 setup、测 Codex 联网。
- **决定是怎么做出来的**：结构性的方案大多由 agent 提出（仓库形态、目录、按句定时、技能冲突的处理），用户一轮就采纳；环境和工具的事实大多由用户纠正（GPU、只用 DispatchDock 的技能、Codex 能联网、提交信息会丢信息、本地目录名）。一共 4 轮对齐，每轮用户都是"采纳大部分 + 纠正几处"。
- **最大的代价**：拆解参考视频时读了 27 张图，上下文在 26 分钟里从 3.7 万涨到 25.5 万 token，之后每一次调用都要重读。落地阶段 43 次调用读了 1,726 万缓存 token，比拆解阶段 96 次调用读的还多。
- **交接靠一份没人要求过的路线图**：`docs/roadmap.md` 是 agent 自己加的，没有任何技能或规则指导过它，却成了之后每个会话的入口。
- **后来的检验**：静态的规则（`AGENTS.md` 的结构、角色分工、工单放在 GitHub、提交格式）基本没改，`AGENTS.md` 到现在净改动只有 8 行增、6 行删；动态的执行流程（`studio-tickets`）在第一次真正使用后被整体重写成 `run-spec`。

规律：

- **结构由 agent 提，一轮通过。** 仓库形态、目录、按句定时、技能冲突的处理，都是 agent 读完材料后提出的，用户没有改动。
- **环境事实由用户纠正。** GPU、DispatchDock 的用法、Codex 联网、本地目录名，都是 agent 在用户机器上的假设，用户凭自己的了解或实测推翻。其中 Codex 联网一条，用户在会话外测了 3 分钟，就推翻了一套快照机制。
- **用户的取舍和推荐不完全一样。** 删技能时有 4 处和推荐不同，工单系统没选推荐的本地 markdown。"全部按推荐"只发生在用户认为 agent 更懂的技术细节上。

## 4. 双方各自起的作用

### 用户

- **开口前备齐材料和工具。** 第一条消息发出时，参考视频、DispatchDock、两套技能、Codex 都已就位。agent 不用来回要东西，26 分钟内产出 6 份拆解文档。
- **在动手前叫停对齐，并补上真正的目标。** 17:47 那条消息把"复刻一个开场"扩成了"做视频、探索 DispatchDock、复利"三个目标，仓库从"一个视频项目"变成"工作室"。后面所有结构性决定都建立在这三个目标上。
- **在 agent 的盲区上纠正。** 每一处纠正都来自 agent 看不到或没有实测的东西：本机硬件、自己打算怎么用 DispatchDock、技能装全了没有、Codex 的实际权限、提交历史将来怎么读。
- **用实测回答事实问题。** Codex 能不能联网，用户没有和 agent 讨论，而是去测了，然后带着结果回来。
- **控制会话边界和节奏。** 两次打断（停掉等待循环问 GPU、在方案写到一半时补充 DispatchDock 的用法）；决定彩排换会话；交接前检查路线图会不会影响新会话；要一份逐步的输入指南。
- **在对齐够了的时候放权。** 三轮对齐后："其他的没有问题，可以按照你的分析来，如果看完有需要修改的你可以直接进行改动。"彩排会话里也是"你是这方面的专家，比我在这方面要擅长，全部按你的推荐来"，但只针对技术细节；范围问题（第一阶段要不要一起做）用户自己定。
- **会话外并行动手。** 修权限、换包管理器、增删技能、跑 setup、测 Codex，都在 agent 等回复的时间里完成。

用户在记录里的评价，原话照录：17:55"你的分析和建议很好，都进行采用"；18:21"你的分析非常好，大部分是正确的"；23:10 发起本次复盘时"我与 agent 一起协作来新建这个仓库的整个过程我觉得非常好"。

### agent

- **先读后说。** 提方案前读完了 DispatchDock 的文档和脚本、Matt 技能的 setup 和主流程、Remotion 技能里关于多场景的说明，并空跑了派发脚本。方案里的理由多数能指回读到的原文或实测。
- **每次长回复都以"要你决定的事"收尾，并给推荐。** 用户回复时只需要处理不同意的地方。
- **补上用户没想到的。** git 属主问题、技能之间缺的依赖、Codex 能看到 `.agents/skills/`、流程技能只能手动调用、`code-review` 重名、`tdd` 在后台没法问人、DispatchDock 的注释要求和用户的注释规则冲突、Codex 自带生图技能、`tsc` 的基线就是坏的、推送前检查媒体和密钥、路线图会影响新会话、一条没确认过的建议被写进了路线图。
- **自主执行时报备。** 用户放权后，agent 自己定的事在结尾单独列出，包括一处本机全局配置的改动和撤销方法。
- **用实测代替推断。** 冒烟测试、`git check-ignore`、尾注解析、改名后在新路径下空跑派发，都是做完立刻验证。
- **失误**：
  - 没先探查环境就假设没有 GPU、Codex 不能联网。前者让转写从 17:01 拖到 17:20，中间换了三次方案，换 GPU 后两分钟就转完；后者让一套快照机制白设计了一轮。
  - 写了两个等待循环，其中一个被用户拒绝；`codex-dispatch` 技能本来就说不要轮询，靠完成通知即可。
  - 照搬了参考项目的提交格式，没有判断它在这个仓库里是否合适。
  - 建远程仓库时只用了新名字，没改本地目录。后来改名让建仓会话的记录留在旧目录里，这次复盘找记录时就要两边都看。
  - 拆解文档里两个数字算错，自己复核时发现并改正。

## 5. 建仓时的安排后来怎样了

依据：`docs/research/rehearsal-findings.md`、两份 spec 汇报、`2433849` 到现在的 git 差异、会话 2～4 里用户的原话。

### 保留下来的

| 安排 | 后来 |
|---|---|
| `AGENTS.md` 的结构：角色、共同规则、目录与归属 | 结构没变。到现在净改动 8 行增、6 行删，全是补充：验证命令换成 `pnpm verify`、提交格式由钩子和 CI 检查、依赖方向写成规则 |
| 角色分工和判断标准（描述明显比实现短、结果能客观验收的才派出去） | 角色文档里这一节没改过 |
| 工单只在 GitHub 上一份，按 issue 号派发，Codex 用完全权限 | 写进路线图「已定」，至今未变 |
| 两套标签：Matt 的分诊标签和执行角色标签 | 彩排复盘时用户决定"都留着" |
| 提交格式 | spec #1 做成 commit-msg 钩子和 CI 检查 |
| 依赖方向（`src/`、`tools/` 不引用 `episodes/`） | spec #1 做成 `pnpm verify` 里的检查 |
| 彩排换干净会话 | 推广为"`/to-tickets` 之后开新会话执行 spec" |
| 第三方技能不进 git，按锁文件和安装器重装 | `run-spec` 的迁移包沿用了这条 |
| 交接指南 | 彩排会话的开场白照着第 1 步输入 |

### 被改掉的

| 建仓时 | 改成 | 原因 |
|---|---|---|
| `studio-tickets`：一份技能写全部步骤，混着本仓库的值 | `run-spec`：通用步骤 + 本仓库配置 + 工单脚本（`dispatch`、`land`、`accept`、`cleanup`） | 彩排里手工准备 worktree 的步骤是固定的；用户提出这套要迁移到别的仓库 |
| 工单写"写入范围"，到目录一级 | 可选的「边界」，用功能描述，不写路径 | 用户在彩排复盘时定："不写文件路径"是正确的，由执行 agent 自己查看和决定 |
| Codex 一次只跑一张工单 | 可做的工单各开一个 worktree 并行，最多三路 | 用户在彩排中提出 |
| 设计负责人逐张工单跑 `code-review` | 每批合并后和 spec 收尾时由 Codex 审查，设计负责人取舍 | 用户觉得逐张审查繁琐；审查子代理的 token 花在了 Claude 这边 |
| 没有汇报 | spec 收尾写汇报存进仓库，从 spec #17 起是 HTML 页面 | 用户要求向自己汇报工作，并补上执行时间和 token 用量 |
| PR 合并方式没约定 | 只允许 merge commit | 彩排的 PR 被 squash 合并，工单和提交对不上 |
| 讨论时把所有问题都抛给用户 | 先问要用户拍板的（范围、取舍、费用、审美），技术细节给推荐、默认按推荐 | 彩排讨论两轮 18 个问题，用户全部按推荐通过 |

### 还没经过检验的

按句定时、`src/kit/` 和 `episodes/` 的分层、风格皮肤，要等第一阶段做镜头时才用得上。

### 一条规律

建仓时写下的**静态规则**（结构、角色、约定、放在哪里）几乎原样保留；**执行流程**（工单怎么派、怎么审、怎么收尾）在第一次真正使用后被整体重写。建仓时在执行流程上花的精力，大部分后来都改写了，而彩排找出这些问题只用了一个 spec。所以开局时规则可以写得认真，执行流程写一个能跑的最小版本，然后尽快安排彩排。

## 6. 路线图：没人要求，却成了每次会话的入口

**来历**。会话 1 里没有人要求写路线图，它分两步演变而来：

1. 17:15，agent 拆解参考时主动写了 `docs/rebuild-plan.md`（重建计划），是 6 份拆解文档之一，依据是用户第一条消息里的"分析、拆解和重建整个制作方法和流程"。文件头写着"方案，待用户确认后实施"，内容是本机现状、目标、分阶段计划和待定事项。
2. 18:57，用户决定彩排换到干净会话之后，agent 趁冒烟测试的空档把它改名为 `docs/roadmap.md` 并重写，推理记录里写的是"供你在新会话中继续使用"。重写后分为目标、已定、进度、下一步四部分，文档地图里标上"新会话从这里看起"（`afb7b1c`）。19:00 和 19:38 两次交接，agent 都让用户在新会话的第一句说"先读 `docs/roadmap.md`"。

Matt、DispatchDock、Remotion 三套技能都没有提到路线图。最接近的是 Matt 的 `handoff`，但它要手动运行，写的是一次性的会话摘要，存在系统临时目录，不进仓库。

**作用**。会话 2、3、4 和本次复盘的第一句都是"你的角色是设计负责人。先读 docs/roadmap.md"。路线图不会被自动加载（自动加载的只有 `CLAUDE.md` → `AGENTS.md`），它能起作用，靠的是用户每次在开场白里点名。三个目标、已定的决策、进度和下一步都在这一个文件里，新会话读完就能接上，不用回看之前的对话。

**代价**。

- 从 `rebuild-plan.md` 算起，不到 18 小时有 13 个提交改过它。
- "已定"和"进度"两张表是其他文档的摘要副本，出处一改，路线图就可能过时。19:33 agent 就提过这个风险。
- 没有任何规则说明谁、在什么时候更新它，一直是设计负责人顺手改的，比如 `ea669e6` 标记 spec #17 完成。
- 没有约定任务全部完成以后怎么处理它。

开局清单把它列成了交接那一步的第一项，并写明了内容、更新时机和收尾办法。

## 7. 起作用的做法和付出的代价

### 起作用的

1. **人先备齐材料和工具，再开口。** agent 的第一段工作完全不用等人。
2. **先拆解参考，再讨论结构。** 结构方案里的关键理由来自拆解：按句定时出自另一位作者说的"改配音就要重新对齐"，"描述比实现短才派出去"出自 DispatchDock 的分工规则。
3. **人主动叫停对齐，agent 用"结论、理由、要你决定的事和推荐"回应。** 4 轮对齐，用户每轮回复都是"采纳 + 几处纠正"，没有出现推倒重来。
4. **事实问题用实测回答。** 用户测 Codex 联网，agent 用冒烟测试回答"Codex 看不到 DispatchDock 行不行"。
5. **放权以后报备。** 用户放权后 agent 自己定了几件事，最后都单独列给用户看，没有一件事是用户事后才发现的。
6. **纠正一次，改在一处，同步各处。** 提交格式改正时，agent 先找出所有旧写法，规则只留 `AGENTS.md` 一处；后来再做成钩子，就不再靠记忆。
7. **交接前检查新会话会读到什么。** 去掉评估清单和越权的指令，标出没确认过的建议，再给出逐字的开场白。
8. **留一份路线图作交接入口。** 目标、已定、进度、下一步放在仓库里的一个文件中，每个新会话从它开始。

### 付出的代价

1. **重度的感知工作和后面的讨论放在同一个会话里。** 27 张图让上下文在第一段就到了 25 万，后面每次调用都在为它付费。
2. **环境事实靠假设，没有先探查。** GPU 和 Codex 联网两处假设，各让一段工作返工。
3. **照搬参考项目的约定。** 提交格式是从 DispatchDock 原样拿来的，用户指出会丢信息才改。
4. **命名定得晚。** 建仓用的是临时名 my-video，远程仓库用了新名字，本地目录没跟上，后来改名又让会话记录分散在两个目录里。
5. **用 root 建仓。** 第一条 git 命令就失败，要用户手动修权限。

## 8. 换一个仓库怎么开局

按上面的经验整理成了 `docs/workflow/bootstrap.md`：人在开口前要准备什么、agent 第一件事先探查环境、拆解参考放在会话之外、对齐要定哪些事、落地和冒烟测试怎么做、怎样写路线图并交接给彩排。清单里标出了哪些步骤适合交给路线图上的迁移初始化技能（`setup-run-spec`），作为那份 spec 的输入。
