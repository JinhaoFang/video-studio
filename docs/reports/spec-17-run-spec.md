# Spec #17 汇报：工单脚本补齐与技能改名（run-spec）

2026-10-12 · 设计负责人 → 用户 · [spec #17](https://github.com/JinhaoFang/video-studio/issues/17) · [PR #31](https://github.com/JinhaoFang/video-studio/pull/31)（待合并）

**一句话**：执行技能改名为 `run-spec`，每张工程工单从近 10 步手工操作变成 `dispatch`、`land` 两条命令；这个 spec 自己从 #21 起就用新命令执行。按批审查第一次交给 Codex，四次审查查出 9 条问题，全部修完。设计负责人这边的 token 用量降到 spec #1 的四成左右。

## 任务

把彩排复盘里需要写代码的调整做完：

- 工单脚本补上 `dispatch`、`land`、`cleanup`；`accept` 自动写入派发数据；`link` 精简输出。
- `pnpm verify` 加一项护栏：规则文档里写的命令必须存在。
- 执行技能改名 `run-spec`，本仓库特有的值挪进配置，做到"复制技能、写一份配置就能迁移"。

同时检验复盘定下的两条做法：执行放在新会话；审查按批交给 Codex。

## 交付

- **两条命令走完一张工单**：`dispatch <T>` 建 worktree、接软链接、装依赖、派给 Codex，等它结束；`land <T>` 依次做 rebase、验证、快进合并、推送、复制记录、删 worktree，停下后修好重跑同一条命令就能接着做。名字由脚本决定，不用再起英文短名。
- **过程数据自动留在 GitHub**：`accept` 把每次派发的用时和 token 写进验收评论，清理本地记录后写汇报照样有数据。
- **收尾一条命令**：`cleanup <S>` 只删本 spec 的记录、产物、worktree 和分支，其他记录保留。
- **文档不会再悄悄过时**：规则文档里写了不存在的 `pnpm` 脚本或 `node` 路径，`pnpm verify` 和 CI 都会失败。
- **可迁移**：技能目录不再引用 `tools/`；本仓库特有的值在 `docs/agents/run-spec.json` 和 `run-spec.md`，后者写了迁移步骤。

## 问题与处理

- **读工单的命令一直是错的，我漏看了信号。** 派发指令和工程负责人角色文档都写着 `gh issue view <号> --comments`，在本机的 gh 2.83 上它只输出评论，不输出正文。spec #1 起的每次派发都受影响，Codex 每次都自己改用 JSON 读取，所以没出事。会话一开始我自己就遇到了一次空输出，#21 的汇报也在「偏离说明」里写了这件事，但我都没追，直到收尾审查才查出来，由 #29 修复。教训：汇报里的「偏离说明」要当作信号来查。
- **评论里写错了数据，已更正。** #21 的用时，我第一次写成了进度日志里的时间戳（约 23 分钟），实际是 7.1 分钟；#23 的缓存数少了千位分隔符。两处都已改。这也说明 #22 让 `accept` 自动取数是对的。
- **审查期间往集成分支提交了 #24。** 违反了"审查跑完前不合并"。第三批审查把起点时的提交定为终点，#24 没有混进这一批，由收尾审查覆盖，没有影响结果。
- **本机 pnpm 入口异常**：报告的版本是 10.34.6，安装元数据却是 12.9.1，`pnpm help --all` 也失败。#26 改用官方发布包核对，绕开了这个问题。入口本身没处理，留作遗留。

## 流程发现

1. **执行放新会话、审查交给 Codex，两条都有效。** 设计负责人的缓存读取降了约六成，结束时上下文约 25 万。剩下的大头是验收时读汇报、看 diff。
2. **工具用来执行自己，问题暴露得早。** `land` 合并了自己，改名挪走了正在用的脚本，两次 rebase 冲突都是真实场景。`land` 合并后失败不能续做的问题，也是在实际用的时候想到、再交给审查确认的。
3. **工程工单顺手改技能文档，会留下过渡期的不一致。** #21～#23 各改了几行技能文档，第二批审查报了步骤不一致。#24 整体改写后消除。只要改写工单排在后面，这样做没问题。
4. **审查指令里列出已安排的问题，能避免重复报告。** 第三批和收尾审查都这样做了，报告里没有重复项。
