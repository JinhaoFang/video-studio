交付了什么

  • run-spec v3

    工单脚本从 8 个子命令变成 13 个：新增 verify（只看尾部、退出码照实）、pr-check（CI 不能用时跑本机 CI）、watch（小模型巡检长作业）、review-spec（派发前的独立审查）、slots（看名额）。dispatch 到并发上限自动排队、中断后 --resume 原地续做、只让 Codex 读 spec 正文；land 把工单生成的被忽略文件移到保留目录，不再删掉。说明文件和 report.md 按这些改写，附图优先的汇报模板。

  • setup-run-spec v3

    角色模板只生成仓库规则，本机的坑和个人习惯分出去；新增「项目对设计负责人的要求」、写给没参加讨论的人、执行中重新判断、派发前独立审查。setup 会提议拆共享登记处、只追加列表设 union 合并（本地 merge 和 rebase 实测生效）、每个目录一个 README、可选的画图约定，交接写上后台会话的启动方式。

  • PathJX 升级的输入

    PathJX 第一阶段结束时的 404 条规则逐条归到三层，并用 v3 模板为它重新生成三处规则：合计 10,117 字节，不超过 v2 生成时的 10,145（第一阶段结束时已涨到 16,526）。在 docs/research/pathjx-rule-layers.md。

  • 对你意味着什么

    可做的工单多于 Codex 名额时不会再被拒；几个小时的作业不用盯；生成的媒体、克隆的参考仓库不会随合并消失；开新会话只说一句"你的角色是设计负责人，先读路线图"。本仓库已切到 v3，配置说明里有升级须知。

    遇到了什么

    • 我验收 #86 时漏了一条

      你在执行中给 #86 加了"后台会话的启动方式"，我验收时读的还是修订前的正文。第一次按批审查发现，当场补上。之后每张工单验收前都重读了正文。

    • 两张工单在子命令登记表上冲突

      #85 派出时 #83 还没合并，两边在同一处各加一项，合并时 rebase 冲突。这个会话不能对别的 worktree 跑 git，就派了一个 0.8 分钟的小任务完成 rebase。之后的 #82、#84 指定了不同的插入位置，没有再冲突。

    • 两张工单合在一起才出现的问题

      #79 的测试会真的调用 dispatch，#85 之后 dispatch 读本机真实的派发记录，于是本机已有两个 Codex 在跑时 pnpm verify 会卡住。#82 的 Codex 发现，返工单 #89 修好。

    • land 的保留清单每次都有内容

      已经复制回主工作区的记录和验收产物也被列出来，读的人会习惯性忽略。#79 验收时发现，#89 修好；之后 #87、#88 的合并已不再列。

    • 设计负责人用量偏高

      主会话是 Codex 的约 2.2 倍（spec #60 是 0.53，PathJX 第一阶段是 0.93）。三张设计工单都是长文档改写，反复量篇幅；主会话平均上下文约 34 万 token。下次可以把量篇幅、核对旧写法这类事做成脚本，或在里程碑处交接到新会话。
