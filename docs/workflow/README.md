# 制作工作流

一项工作从想法到合并，谁在什么时候用什么。具体步骤写在各技能和角色文档里，这里是总图。

## 一项工作的生命周期

| 阶段       | 谁触发                                          | 用什么                                         | 产物在哪                                                             |
| ---------- | ----------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------- |
| 想清楚     | 用户                                            | `/grill-with-docs`                             | 术语进 `GLOSSARY.md`，难回头的决定进 `docs/adr/`                     |
| 写 spec    | 用户                                            | `/to-spec`                                     | GitHub issue                                                         |
| 拆工单     | 用户                                            | `/to-tickets`                                  | spec 的 sub-issue，带阻塞关系；格式见 `docs/agents/issue-tracker.md` |
| 执行与验收 | 用户在新会话里说"执行 spec #号"，设计负责人照做（会话可以放在后台，见下文） | `run-spec`（自带派发层，按席位选框架和模型）   | 集成分支上的提交、工单下的验收评论、`docs/reports/` 的汇报           |
| 合并       | 用户                                            | PR（正文用 `/pr` 的格式），只能用 merge commit；改了工作室层的先在新会话审一次（见「复利」） | `main`                                                               |
| 复盘       | 用户                                            | 新会话里跑 `/retro`（见「复利」）              | 规则文档、检查脚本、文档指针                                         |

执行阶段的回路：

```
GitHub                        设计负责人（主会话）                           工程负责人（按席位派发的 agent）
spec #S     ─ 确认基线（verify）；由用户决定是否启动派发前独立审查，选择后按 run-spec 做（review-spec）
 └ 工单 #T  ─ 选出前置都已关闭的工单
   role:design      → 自己做、验收、提交
   role:engineering → 按 issue 号派发，到并发上限排队 ───────────→ 读 #T 的正文和评论、#S 的正文，做完、提交（Refs: #T）、写汇报
                     ← 看汇报（TODO(design)、推断清单）、实测验收产物 ←──────────┘
   ready-for-human  → 告诉用户要做什么
 └ 合并、评论验收结论、关闭 #T；每批合并后派审查席位审查；全部关闭后再审一次、开 PR "Closes #S"、查 PR（pr-check）、写汇报、清理
```

执行会话可以放在后台跑（可选）：`claude --bg -n <名字> --permission-mode <和平时相同的模式> "<开场白>"` 启动，`claude attach <名字>` 进入；在里面按 ← 回到会话列表、按 Ctrl+Z 回到 shell，会话都继续运行。`claude agents` 看有哪些会话，`claude logs <名字>` 看最近的输出，`claude stop <id>` 停下。后台会话不依附终端，关掉终端不会中断派发出去的执行者；前台会话在派发运行期间要一直开着。权限模式要和平时一致，不一致时碰到确认就停下等人。

## 什么放在哪里

- **GitHub**：spec、工单、验收评论、PR。它们是过程记录，只存这一份。
- **仓库**：长期有效的东西，包括规则（`AGENTS.md`、角色文档、本文件）、术语与 ADR、研究、每期的台本和镜头剧本、代码和工具。工单要用仓库里的文件时写路径，不复制内容。
- **只在本机**：`.codex-runs/`（派发记录、进度、原始日志）；媒体放 `public/episodes/`，渲染输出放 `out/`。
- **各类文档的职责**：路线图只放目标、已定（索引）、下一步和待定；汇报一个 spec 一份；研究目录放调研和证据，结论数字只写在一处，别处链接。草稿、工作表、回执、核验记录是工单的验收产物，放 `out/qa/`，不进 `docs/`；要留的结论并进现有文档。新增文档前先找能并入的；被链接不是保留的理由。

## 护栏

能机械判断的规则交给护栏，不靠自觉：

- `pnpm verify`：步骤见 `tools/verify.ts`，运行时每步先打印 `[verify]` 标签；`pnpm verify --static` 跑除测试以外的全部步骤。合并前跑哪一层由工单脚本按改动路径选，配置见 `docs/agents/run-spec.md`。设计负责人用工单脚本的 `verify` 子命令跑它：屏幕只看尾部和一行结论，完整输出进日志，退出码照实，不用 `| tail` 这种会吞掉退出码的写法。
- commit-msg 钩子：按 `AGENTS.md` 的格式检查提交信息。
- CI：开 PR、推送 `ticket/**` 和手动触发时跑 `pnpm verify`，并逐条检查分支上的提交信息，兜住绕过本地钩子的提交。工单分支只有派发时加了 `--allow-push` 才会被推上去。集成分支 `spec/**` 推送时不跑：`land` 合并每张工单前已在本机跑过同样的验证。同一个 PR 的新运行会取消还没跑完的旧运行。本地复现：`pnpm verify`，再 `pnpm check:commits origin/main <分支>`。收尾时工单脚本的 `pr-check` 等 PR 的检查跑完。CI 启动不了时（用户 10-31）：GitHub Actions 的设定不动，改为本机验证。判断办法：`gh run view <运行号>` 里作业一步都没跑就失败，注解写 `The job was not started`（例如 10-29 起的账号计费问题）。在 PR 分支上跑上面两条本地复现命令，把结论评论到 PR，代替这次的 CI 结果。

pnpm 的版本由 `package.json` 的 `packageManager` 固定，本机装的 pnpm 会自动切换到这个版本，本地和 CI 一致。文档命令护栏会检查内置命令白名单版本是否一致；升级时按 `tools/check-doc-commands.ts` 文件头的方法更新白名单和版本。

规则文档命令检查的范围和规则写在检查脚本的文件头，运行 `node tools/check-doc-commands.ts --help` 查看用法。研究记录和工作汇报不在范围内，可以如实保留历史命令。

## 一期视频

一期对应一个目录 `episodes/<期>/`；要不要写 spec 由用户决定，写了的话一个 spec 对应一期。目录里放本期说明、台本、镜头剧本、`sources.md`、`data/` 下的生成数据和本期镜头代码。

开一期时，设计负责人按下面 13 项检查该定的事都定了。它是设计负责人自己的清单，不是问用户的问卷：哪几项请用户参与、怎么问，见 `docs/roles/design.md`「工作流」；每项有哪些选项、各是什么意思，见 `docs/video/`。

| 阶段 | 决定 | 知识 |
|---|---|---|
| 策划 | ① 目的与受众　② 渠道与规格（平台、画幅、时长、开头怎么抓人）　③ 类型与基调　④ 叙事结构与文案 | `planning.md` |
| 视听设计 | ⑤ 画面风格（含色彩、字体）　⑥ 素材来源　⑦ 镜头语言　⑧ 声音（旁白、配乐、音效） | `visual-style.md`、`camera.md`、`sound.md` |
| 后期 | ⑨ 剪辑（节奏、转场、剪辑手法）　⑩ 画面文字　⑪ 调色与质感　⑫ 混音与响度 | `editing.md`、`sound.md` |
| 交付 | ⑬ 封面、多版本、授权 | `delivery.md` |

本期说明开头一节「决定」列出 13 项的结论，每项一行，理由一句话；制作中才定下的项随时补上。这一节从 2026-11-09 起的新期开始写，之前的两期没有。

镜头剧本 `storyboard.md` 一个镜头一行，列为：镜头、句子范围、参考段落（复刻时）、画面、运镜。运镜一列写清镜头跟着谁、揭示什么、停在哪里；同一素材上换景别写成推拉或横移，换素材、换场景才写溶解或切，规则见 `docs/roles/design.md`「镜头运动」。复刻参考时，这一列要按 10fps 以上的密集帧核对后再写。示例见 [NASA 朋克开场镜头剧本](../../episodes/nasa-punk-opening/storyboard.md)。

时间机制：台本每句一个编号（`L001`、`L002`……）和句后停顿，以每句音频的实测时长累计生成时间轴，记录每句的起止帧和配音来源。镜头代码按"某句开始后多少帧"定时，不写死帧号。改稿或重配音后重新生成时间轴，动画会跟着走。当前格式、生成工具和 `pnpm qa sentence` 按句取点用法见 [NASA 朋克开场说明](../../episodes/nasa-punk-opening/README.md)。

配音和成片的工具先看 `--help`：逐句配音 `pnpm tts`、等比变速 `node tools/stretch-voice.ts`、配音打分 `pnpm qa voice`、配乐与混音 `node tools/mix-opening.ts`、运动自检 `pnpm qa motion`。本期的复现命令见 [NASA 朋克开场说明](../../episodes/nasa-punk-opening/README.md)。`--help` 里没有的几条：

- 凭据只从环境变量或 `--env` 指定的文件读，不复制进仓库和日志。
- `eleven_v4` 不支持 Speed，请求成功不代表生效（[API 研究](../research/nasa-ep04/elevenlabs-api.md)）。
- 变速总是从原始目录生成到新目录；时间轴读变速后的实测时长，来源说明写明默认倍率和例外。
- 成片响度用 `pnpm qa loudness` 验收：目标 -16 LUFS、容差 1 LU、真峰值不超过 -1 dBTP，LRA 只报告。
- 配音打分的截断标记和运动自检的检出都是复核线索，结合原始转写或画面再下结论。

白板手绘段落可以用外部技能 `srt-whiteboard-animation`（MIT，登记在 `skills-lock.json`）：它把一张线稿按字幕分区，用连续笔迹画成 MP4，作为视频素材放进 Remotion 合成。几点约定：

- 线稿和渲染出的 MP4 放 `public/episodes/<期>/`，渲染脚本的输出路径是参数。成片画幅等于线稿的像素尺寸，要 1920×1080 就给 1920×1080 的图。
- 线稿由用户提供，或另配生图工具；本仓库的 agent 不生成图片。
- 内置的手部图带作者标识，正式使用时换成自己的手部图，或用 `--bare-tip` 不画手。
- 它自带的「每步等用户确认」不代替本仓库请用户参与的时机（`docs/roles/design.md`「工作流」）。
- Python 依赖装在技能自己的虚拟环境里，不进 `package.json`；本机缺 `ensurepip` 时的绕法和实测见 [白板技能研究](../research/srt-whiteboard-animation.md)。

## 复利

工作室层（规则文档、`tools/`、`src/kit/`、`src/styles/`、术语、路线图）是每个用户下一期的起点，它的质量靠下面的入口、标准和审查来保证，不靠某个人审批（[ADR 0001](../adr/0001-studio-layer-without-gatekeeper.md)）。

- **入口**：一期做完后，开一个新会话跑 `/retro`，读制作会话的原始记录，列出改进候选，用户挑选后再改工作室层。制作会话只做这一期需要的改动：本期目录、在 `episodes/Root.tsx` 登记合成、修工具 bug、第二次用到时把代码提进 `src/kit/`；经验、规则和立场的沉淀留给 retro。每个 spec 结束也跑一次。
- **看什么**：除了 retro 自带的几类，本仓库还要看制作经验：好用的镜头做法、缺的工具、踩过的坑。能机械检查的错误做成检查脚本或钩子，需要判断的写进规则文档，找东西费劲的地方加文档指针。
- **标准**：沉淀到工作室层的内容要满足：
  1. 只写事实和方法，附出处；不写评价和立场。
  2. 换一个人或一台机器仍然成立的才写进规则；只在某台机器上成立的写进本机说明。
  3. 工具和命令在仓库里能复现；只在本机做过的步骤标成"本机步骤"。
  4. 和已有文档冲突时，把冲突列出来，不悄悄覆盖。
- **推翻已定事项**：新增随意；推翻路线图「已定」或规则文档里的决定时，在 PR 里请当初定这条的人确认。
- **合并前审查**：改了工作室层的 PR，合并前在作者会话之外开一个新会话，用 `code-review` 审一次，结论评论到 PR，之后作者可以自己合并。只改期目录的 PR 不需要。
- 第二次用到的代码提到 `src/kit/`，第二次用到的风格提到 `src/styles/`。
- 满意的镜头记下来作为对标片，以后同类镜头照着它验收。

## 方法层仓库

开发流程（`run-spec`、`setup-run-spec`，以及它们的观察记录、规则判定标准、开局步骤和各版本汇报）2026-10-31 用 `git filter-repo` 带着历史拆到 `JinhaoFang/agent-workflow`，提交尾注改成了 `Refs: JinhaoFang/video-studio#号`，链接仍指向本仓库的 issue。

- 本仓库的这两个技能和别的仓库一样从新仓库安装，不进 git，版本记在 `skills-lock.json`；改动去新仓库做。
- 视频的组件和风格（`src/kit/`、`src/styles/`）、工具（`tools/`）、规则文档和护栏留在本仓库。拆分前曾设想把它们也算作方法层；实际用方法层的是 PathJX 和 design-system，它们用不上视频组件，规则和护栏也是每个仓库按自己的工具链写。

## 注意

- 派发、合并、验收、审查、收尾的具体步骤只写在执行技能 `run-spec` 里，本仓库特有的值见 `docs/agents/run-spec.md`。
- `code-review` 重名：用 Skill 工具调用 `code-review`，加载的是仓库里 Matt 的版本（Standards、Spec 两条线并行的子代理审查）。用户在输入框直接打 `/code-review` 时调用哪个，没有实测。
