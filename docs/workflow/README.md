# 制作工作流

一项工作从想法到合并，谁在什么时候用什么。具体步骤写在各技能和角色文档里，这里是总图。

## 一项工作的生命周期

| 阶段       | 谁触发                                          | 用什么                                         | 产物在哪                                                             |
| ---------- | ----------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------- |
| 想清楚     | 用户                                            | `/grill-with-docs`                             | 术语进 `GLOSSARY.md`，难回头的决定进 `docs/adr/`                     |
| 写 spec    | 用户                                            | `/to-spec`                                     | GitHub issue                                                         |
| 拆工单     | 用户                                            | `/to-tickets`                                  | spec 的 sub-issue，带阻塞关系；格式见 `docs/agents/issue-tracker.md` |
| 执行与验收 | 用户在新会话里说"执行 spec #号"，设计负责人照做（会话可以放在后台，见下文） | `run-spec`（自带派发层，按席位选框架和模型）   | 集成分支上的提交、工单下的验收评论、`docs/reports/` 的汇报           |
| 合并       | 用户                                            | PR（正文用 `/pr` 的格式），只能用 merge commit；改了工作室层的先在新会话审一次（见「复利」） | `main`                                                               |
| 复盘       | 用户                                            | 新会话里跑 `/retro`（见「复利」）              | 规则文档、检查脚本、文档指针                                         |

执行阶段的回路：

```
GitHub                        设计负责人（主会话）                           工程负责人（按席位派发的 agent）
spec #S     ─ 确认基线（verify）；由用户决定是否启动派发前独立审查，选择后按 run-spec 做（review-spec）
 └ 工单 #T  ─ 选出前置都已关闭的工单
   role:design      → 自己做、验收、提交
   role:engineering → 按 issue 号派发，到并发上限排队 ───────────→ 读 #T 的正文和评论、#S 的正文，做完、提交（Refs: #T）、写汇报
                     ← 看汇报（TODO(design)、推断清单）、实测验收产物 ←──────────┘
   ready-for-human  → 告诉用户要做什么
 └ 合并、评论验收结论、关闭 #T；每批合并后派审查席位审查；全部关闭后再审一次、开 PR "Closes #S"、查 PR（pr-check）、写汇报、清理
```

执行会话可以放在后台跑（可选）：`claude --bg -n <名字> --permission-mode <和平时相同的模式> "<开场白>"` 启动，`claude attach <名字>` 进入；在里面按 ← 回到会话列表、按 Ctrl+Z 回到 shell，会话都继续运行。`claude agents` 看有哪些会话，`claude logs <名字>` 看最近的输出，`claude stop <id>` 停下。后台会话不依附终端，关掉终端不会中断派发出去的执行者；前台会话在派发运行期间要一直开着。权限模式要和平时一致，不一致时碰到确认就停下等人。

## 什么放在哪里

- **GitHub**：spec、工单、验收评论、PR。它们是过程记录，只存这一份。
- **仓库**：长期有效的东西，包括规则（`AGENTS.md`、角色文档、本文件）、术语与 ADR、研究、每期的台本和镜头剧本、代码和工具。工单要用仓库里的文件时写路径，不复制内容。
- **只在本机**：`.codex-runs/`（派发记录、进度、原始日志）；媒体放 `public/episodes/`，渲染输出放 `out/`。
- **各类文档的职责**：路线图只放目标、已定（索引）、下一步和待定；汇报一个 spec 一份；研究目录放调研和证据，结论数字只写在一处，别处链接。草稿、工作表、回执、核验记录是工单的验收产物，放 `out/qa/`，不进 `docs/`；要留的结论并进现有文档。新增文档前先找能并入的；被链接不是保留的理由。

## 护栏

能机械判断的规则交给护栏，不靠自觉：

- `pnpm verify`：步骤见 `tools/verify.ts`，运行时每步先打印 `[verify]` 标签；`pnpm verify --static` 跑除测试以外的全部步骤。合并前跑哪一层由工单脚本按改动路径选，配置见 `docs/agents/run-spec.md`。设计负责人用工单脚本的 `verify` 子命令跑它：屏幕只看尾部和一行结论，完整输出进日志，退出码照实，不用 `| tail` 这种会吞掉退出码的写法。
- 纯代码合成：`node tools/check-guardrails.ts pure-code` 已进入 verify 的静态步骤，按 `episodes/pure-code.json` 的登记逐项检查各期纯代码合成及启动入口的即时依赖，拒绝外部媒体、字体和未登记的动态素材路径；本地生成媒体存在时核对哈希。登记表至少要有一项，每个 ID 都须对应 Remotion 实际注册的合成（写法见下文「工具」的 kit 一段）。生成清单与重建命令见各期的 `sources.md`，渲染前先运行该期的生成器。
- commit-msg 钩子：按 `AGENTS.md` 的格式检查提交信息。
- CI：开 PR、推送 `ticket/**` 和手动触发时跑 `pnpm verify`，并逐条检查分支上的提交信息，兜住绕过本地钩子的提交。工单分支只有派发时加了 `--allow-push` 才会被推上去。集成分支 `spec/**` 推送时不跑：`land` 合并每张工单前已在本机跑过同样的验证。同一个 PR 的新运行会取消还没跑完的旧运行。本地复现：`pnpm verify`，再 `pnpm check:commits origin/main <分支>`。收尾时工单脚本的 `pr-check` 等 PR 的检查跑完。CI 启动不了时（用户 10-31）：GitHub Actions 的设定不动，改为本机验证。判断办法：`gh run view <运行号>` 里作业一步都没跑就失败，注解写 `The job was not started`（例如 10-29 起的账号计费问题）。在 PR 分支上跑上面两条本地复现命令，把结论评论到 PR，代替这次的 CI 结果。

pnpm 的版本由 `package.json` 的 `packageManager` 固定，本机装的 pnpm 会自动切换到这个版本，本地和 CI 一致。文档命令护栏会检查内置命令白名单版本是否一致；升级时按 `tools/check-doc-commands.ts` 文件头的方法更新白名单和版本。

规则文档命令检查的范围和规则写在检查脚本的文件头，运行 `node tools/check-doc-commands.ts --help` 查看用法。研究记录和工作汇报不在范围内，可以如实保留历史命令。

## 一期视频

一期对应一个目录 `episodes/<期>/`；要不要写 spec 由用户决定，写了的话一个 spec 对应一期。目录里放本期说明、台本、镜头剧本、`sources.md`、`data/` 下的生成数据和本期镜头代码。

### 剧组

一期由剧组来做：六个部门，加上设计负责人兼任的导演和制片（`GLOSSARY.md`「剧组」，依据见 [ADR 0003](../adr/0003-crew-base-by-department.md)）。

- **部门是一门专业，不是一张工单**：一张镜头工单通常同时属于摄影和动作，验收时两边的标准都要过。
- **各类片子用同一个剧组，不同的只是各部门的做法**：例如讲解片的美术是风格令牌加照片素材，纯代码动画的美术是色彩剧本、设定和水粉底图。
- **每期六个部门都在**：某个部门这一期沿用现成的，或者用不上，就写「沿用 …」或「不适用：理由」，不能空着。

开一期时，设计负责人按下表检查每个部门该定的决定都定了。编号沿用之前的 13 项，新增 ⑭。这是设计负责人自己的清单，不是问用户的问卷：哪几项请用户参与、怎么问，见 `docs/roles/design.md`「工作流」；每项有哪些选项、各是什么意思，见 `docs/video/`。

| 部门 | 管什么 | 决定 | 知识 |
|---|---|---|---|
| 导演、制片（设计负责人） | 方向和验收；范围、预算、分工、交付 | ① 目的与受众　② 渠道与规格（平台、画幅、时长、开头怎么抓人）　③ 类型与基调　⑬ 封面、多版本、授权 | `planning.md`、`delivery.md` |
| 编剧 | 讲什么，按什么顺序讲 | ④ 叙事结构与文案 | `planning.md` |
| 美术 | 画面静止时长什么样 | ⑤ 画面风格（含色彩、字体）　⑥ 素材来源　⑪ 调色与质感 | `visual-style.md`、`editing.md`「⑪」 |
| 摄影 | 从哪里看，镜头怎么动 | ⑦ 镜头语言 | `camera.md` |
| 动作 | 画面里的东西怎么动 | ⑭ 动作（动法、节奏、表演、特效动画） | `visual-style.md` 各动画条目的关键技法；[motion.md](../video/motion.md) |
| 剪辑 | 多长，在哪里切，怎么接 | ⑨ 剪辑（节奏、转场、剪辑手法）　⑩ 画面文字 | `editing.md` |
| 声音 | 听到什么 | ⑧ 声音（旁白、配乐、音效）　⑫ 混音与响度 | `sound.md` |

本期说明开头有一节「决定」，按部门分组列出各项的结论，每项一行，理由一句话；制作中才定下的项随时补上。这一节从 2026-11-09 起的新期开始写，从 2026-11-26 起按部门分组；之前的期按原来的 13 项写，不回头改。

### 各部门交出什么、怎么自查

自查都在全片装配里做（见「交接」），对照台本里观众的感受、本部门的标准和对标片，不只对照工单写的数值。美术、摄影、动作交付画面时，执行者还要按 `docs/roles/engineering.md`「完成标准」一轮一轮看画面，下表写的是每个部门具体看什么。用不上的交付写「不适用：理由」。

| 部门 | 交出什么 | 交给谁 | 自查 |
|---|---|---|---|
| 编剧 | 一句话梗概；台本：有旁白时分画面、声音两栏，逐句编号；没有旁白时写节拍表，可以并进镜头剧本。每一拍写观众此刻的感受，写明伏笔和回收 | 摄影、声音、剪辑 | 有旁白时，按配音语速估算时长，放得进规格；每一拍都有画面或声音让观众感受到；删掉哪一拍会看不懂；伏笔都回收了 |
| 美术 | 风格令牌；色彩剧本（包括光的方向，附每个镜头一格的缩略条）；按光照分的色指定；角色、道具、场景的设定（场景附平面布局）；底图或素材；质感参数；美术的「绝不能像」 | 摄影、动作 | 眯眼看只剩 3–5 块明暗；第一眼落在主体上；抽色和色彩剧本对照；设定换个角度仍是同一个；相邻镜头的颜色和光向像同一个世界 |
| 摄影 | 镜头剧本；机位图；每个镜头首帧和末帧的构图 | 动作、剪辑 | 运镜区间看密集帧（`pnpm qa sheet --every 0.1`）；首末帧和镜头剧本对得上；对照机位图不越轴；角色朝向一侧留出视线空间，头顶空间合适 |
| 动作 | 动作规则（节奏、预备、跟随与重叠、弧线、缓入缓出、特效动画的规律、动作的「绝不能像」）；关键姿势；画面事件 | 剪辑；画面事件交给声音 | 动作区间看逐帧条（`pnpm qa strip`）；剪影测试（把角色涂黑，姿势仍然读得懂）；检查弧线和间距；关键姿势停得住；画面事件声明在动作真正发生的那一帧 |
| 剪辑 | 时间表或时间轴；全片装配；切点表；画面文字 | 所有部门 | 全片没有黑帧、缺帧；每个切点都按切点表，把前一镜末帧和后一镜首帧并排看；总时长和时间表一致；画面事件和动画用同一份时间数据 |
| 声音 | 听点表，按旁白或对白、拟音、音效、环境声、音乐分层；配音、乐谱、音效、混音；响度报告 | 剪辑 | 响度（`pnpm qa loudness`）；电平图里没有意外的断音和数字静音；音效落在事件帧上；看得见的接触都有拟音；声音远近随景别变 |
| 制片（设计负责人） | 归属表：每个模块、每个镜头目录归谁改；工单拆分和锁定点；每帧预算和资源上限；`sources.md`；交付清单 | 所有人 | 并行的工单改不到同一个文件 |

几个人并行做同一期时，制片的交付写成本期约定。示例见 [纯代码小样的本期约定](../../episodes/pure-code-sample/contract.md)：靠归属表和每个镜头一个目录，A、B 两版合并时零冲突。

### 交接

**全片装配是主干**：开工后的第一张画面工单由剪辑来做，做出全片装配，用占位画面加临时声音，按时间表排好，能渲染、能播放。之后每张工单落地都替换进去。执行者自查和设计负责人验收都在全片装配里看，包括和前后镜头的接缝。之前出过的三次交接错误，都要放进整条片子才看得出来：spec #60 的 1.2 秒黑场，spec #147 切镜时主体从约 62% 跳到约 38%，静默被做成断音。

| 交接 | 例子 | 主人 | 怎么做 |
|---|---|---|---|
| 镜头和镜头之间 | 硬切、遮挡转场 | 剪辑定切点表，摄影写两侧的画面 | 后做的一侧照切点表取景；落地后，执行者在全片装配里把自己的镜头和前后镜头的接缝并排看 |
| 部门交给部门 | 美术的设定交给画镜头的人 | 接收方 | 开工前按上表查上游交来的东西；不合格就写进汇报，找归属人改，不自己凑合 |
| 部门内部 | 作曲交给混音 | 本部门 | 交接写意图，不只写数值：静默写成"不出新的音，环境声不断"，不写"配乐 = 0" |
| 画面和声音之间 | 画面事件交给声音 | 声音 | 画面锁定后开听点会：对着全片装配，逐个画面事件定下声音从哪里进、哪里出、要什么效果，写成听点表；导演批准后再合成和混音 |

切点表一个切点一行，写三件事：

- **接法**：从 `docs/video/editing.md`「⑨ 剪辑」里选，例如硬切、切在动作上、遮挡转场、甩镜、图形匹配、焦点转场、光转场、叠化、淡入淡出、跳切、声音先行或延后。遮挡、甩镜等接法的特征见[切在动作上](../video/editing.md#切在动作上)至[声音先行或延后](../video/editing.md#声音先行或延后)各条。
- **两侧要对上什么**：主体位置、屏幕方向、轴线、视线、景别或角度差、动作和道具状态、光和颜色、相机运动、声音。
- **哪里故意不对上，为什么**。

### 锁定点

上游锁定后，下游才开工；拆工单时，这些锁就是阻塞关系：

- 全片装配的第一版要等台本锁定，时长从台本来。
- 每个镜头的构图要等全片装配第一版（时长、切点表），以及美术的设定和色彩剧本。
- 动作要等本镜的构图。
- 画面锁定要等全部镜头落地。听点会、最终混音和质感的最终调整，都要等画面锁定。

没有先后关系的照样并行，例如编剧和美术，或者同一道锁之后的几个镜头。锁定以后要改，由导演决定，并通知受影响的下游。

### 镜头剧本

镜头剧本 `storyboard.md` 一个镜头一行，列为：镜头、句子范围、参考段落（复刻时）、画面、运镜。

- **运镜一列**：写清镜头跟着谁、揭示什么、停在哪里。同一素材上换景别，写成推拉或横移，规则见 `docs/roles/design.md`「镜头运动」。
- **镜头之间怎么接**：写进切点表。切点两侧都写主体在画面上的位置（例如横向约 60%）和朝向，后一镜照着取景，这样不同人做的两个镜头也能接上（`docs/video/editing.md`「视线引导」）。
- **复刻参考时**：运镜一列要按 10fps 以上的密集帧核对后再写。

示例见 [NASA 朋克开场镜头剧本](../../episodes/nasa-punk-opening/storyboard.md)。

### 时间机制

按时间轴锚点定时。镜头代码按"某个锚点之后多少帧"定时，不写死全片帧号；改了锚点的位置，动画会跟着走。

- **有旁白时，锚点是台本句子**：台本每句一个编号（`L001`、`L002`……）和句后停顿，以每句音频的实测时长累计生成时间轴，记录每句的起止帧和配音来源。改稿或重配音后重新生成时间轴。当前格式、生成工具和 `pnpm qa sentence` 按句取点用法见 [NASA 朋克开场说明](../../episodes/nasa-punk-opening/README.md)。
- **没有旁白时，锚点是镜头起点和画面事件**：本期有一张镜头时间表（编号、起点、时长），镜头里的动画按镜头起点之后的帧数定时；镜头声明的画面事件汇总成全片事件表，音效按对齐点落到事件帧上。改镜头时长只改时间表。示例见 [纯代码小样说明](../../episodes/pure-code-sample/README.md)。

### 工具

**纯代码动画 kit**。从[小样合成](../../episodes/pure-code-sample/PureCodeSample.tsx)、[样张](../../episodes/pure-code-sample/samples/)和[生成器](../../episodes/pure-code-sample/generate.ts)看调用。新合成在 [纯代码登记表](../../episodes/pure-code.json) 填写 Remotion 注册 ID、源码入口和生成清单。共用入口与清单的版本可合为一项，同目录不同入口各用各的清单。verify 按注册 ID 和入口区分专用加载器，用每项的清单检查该合成和公共启动依赖。

| 模块（相对 `src/kit/`） | 公开接口与用途 |
|---|---|
| `engine/random.ts` | `hash`、`rng`、`noise1/2`、`fbm2` 按种子生成可复现的随机数和噪声。 |
| `engine/timing.ts` | `drawing` 取画张，`hold` 硬停姿势，`progress`、`ease`、`tween` 插值。 |
| `engine/figure.ts` | `ellipsoid`、`roundCone`、`smin` 组合距离场，`sample`、`field`、`contours` 提取轮廓。 |
| `engine/ink.ts` | `boil`、`strokes`、`drawStrokes` 把折线画成有压感、带画张抖动的笔画。 |
| `engine/cel.ts` | `createLayer`、`drawCel`、`placeLayer` 用指定色区、硬边阴影和线条绘制体块。 |
| `engine/paint.ts` | `paper`、`stroke`、`polygon`、`mottle` 在浮点画布上刷水粉，`toBytes` 输出 RGBA。 |

| `engine/post.ts`、`post-settings.ts` | `createPost(canvas)` 创建摄影链。每帧用 `draw(image, frame, post)` 传入包含 `darkest` 的全部后期参数，用完调用 `dispose`。 |
| `shots.ts` | `Shot<Surface>` 声明镜头，`filmDuration`、`locateShot`、`collectEvents` 和 `frameToSample` 共用镜头时间表。 |
| `samples/useFrame.ts` | `useFrame` 等待输入就绪后按帧绘制 Canvas，再应用后期。 |
| `samples/ModelSheet.tsx` | `ModelSheet` 接收各行参考线、视图和角色绘制函数，输出设定图。 |
| `samples/ShotPreview.tsx` | `ShotPreview` 接收镜头、后期基准、输入和 surface 构造函数，随播放头预览或指定局部帧出引擎静帧。 |

已有的按句工具 `sentence-timing.ts` 用 `sentenceFrame`、`chapterSpans` 定时，`subtitle-schedule.ts` 用 `buildSubtitleSchedule`、`subtitleState` 定字幕条。用法见 [NASA 朋克开场](../../episodes/nasa-punk-opening/README.md)。

画面细节与逐帧运动验收：`pnpm qa crop <视频> <时间点> <x,y…>` 按原始像素裁切一个或多个区域，左上角从 `0,0` 起，默认 600×450，可用 `--width`、`--height` 调整；输出不缩放的 PNG，区域超出画面时报错。`pnpm qa strip <视频> --from <起始帧> --to <结束帧> [--every <帧步长>]` 按从 0 开始的解码帧号取样，包含对齐步长的终点，步长默认 1；每格标帧号和实际呈现时间码，默认 4 列、每页最多 24 格，沿用 `sheet` 的排版与 2000 像素整页上限。两项均支持 `--out` 指定输出目录，详细用法见各自 `--help`。

配音和成片的工具先看 `--help`：逐句配音 `pnpm tts`、等比变速 `node tools/stretch-voice.ts`、配音打分 `pnpm qa voice`、配乐与混音 `node tools/mix-opening.ts`、运动自检 `pnpm qa motion`。本期的复现命令见 [NASA 朋克开场说明](../../episodes/nasa-punk-opening/README.md)。`--help` 里没有的几条：

- 凭据只从环境变量或 `--env` 指定的文件读，不复制进仓库和日志。
- `eleven_v4` 不支持 Speed，请求成功不代表生效（[API 研究](../research/nasa-ep04/elevenlabs-api.md)）。
- 变速总是从原始目录生成到新目录；时间轴读变速后的实测时长，来源说明写明默认倍率和例外。
- 成片响度用 `pnpm qa loudness` 验收：目标 -16 LUFS、容差 1 LU、真峰值不超过 -1 dBTP，LRA 只报告。用 `pnpm qa dropouts` 查成片断音，按 JSON 的帧号和时间码在逐帧电平图里复核低电平段与骤降。默认只报告，显式给检测阈值可判定通过与否。
- 配音打分的截断标记和运动自检的检出都是复核线索，结合原始转写或画面再下结论。

白板手绘段落可以用外部技能 `srt-whiteboard-animation`（MIT，登记在 `skills-lock.json`）：它把一张线稿按字幕分区，用连续笔迹画成 MP4，作为视频素材放进 Remotion 合成。几点约定：

- 线稿和渲染出的 MP4 放 `public/episodes/<期>/`，渲染脚本的输出路径是参数。输出尺寸默认把长边缩到 1080，宽高再向下对齐到网格边长（默认 10）的倍数，1920×1080 的线稿默认会出 1080×600；要 1920×1080，给 1920×1080 的线稿并加 `--cap-long-edge 1920`。
- 线稿由用户提供，或另配生图工具；本仓库的 agent 不生成图片。
- 内置的手部图带作者标识，正式使用时换成自己的手部图，或用 `--bare-tip` 不画手。
- 只用它的渲染工具和方法，不执行它自带的七步确认；什么时候请用户参与，按 `docs/roles/design.md`「工作流」。
- Python 依赖装在技能自己的虚拟环境里，不进 `package.json`；本机缺 `ensurepip` 时的绕法和实测见 [白板技能研究](../research/srt-whiteboard-animation.md)。

## 复利

工作室层（规则文档、`tools/`、`src/kit/`、`src/styles/`、术语、路线图）是每个用户下一期的起点，它的质量靠下面的入口、标准和审查来保证，不靠某个人审批（[ADR 0001](../adr/0001-studio-layer-without-gatekeeper.md)）。

- **入口**：一期做完后，开一个新会话跑 `/retro`，读制作会话的原始记录，列出改进候选，用户挑选后再改工作室层。制作会话只做这一期需要的改动：本期目录、在 `episodes/Root.tsx` 登记合成、修工具 bug、第二次用到时把代码提进 `src/kit/`；经验、规则和立场的沉淀留给 retro。每个 spec 结束也跑一次。
- **看什么**：除了 retro 自带的几类，本仓库还要看制作经验：好用的镜头做法、缺的工具、踩过的坑。能机械检查的错误做成检查脚本或钩子，需要判断的写进规则文档，找东西费劲的地方加文档指针。
- **标准**：沉淀到工作室层的内容要满足：
  1. 只写事实和方法，附出处；不写评价和立场。
  2. 换一个人或一台机器仍然成立的才写进规则；只在某台机器上成立的写进本机说明。
  3. 工具和命令在仓库里能复现；只在本机做过的步骤标成"本机步骤"。
  4. 和已有文档冲突时，把冲突列出来，不悄悄覆盖。
- **推翻已定事项**：新增随意；推翻路线图「已定」或规则文档里的决定时，在 PR 里请当初定这条的人确认。
- **合并前审查**：改了工作室层的 PR，合并前在作者会话之外开一个新会话，用 `code-review` 审一次，结论评论到 PR，之后作者可以自己合并。只改期目录的 PR 不需要。
- 第二次用到的代码提到 `src/kit/`，第二次用到的风格提到 `src/styles/`。
- 满意的镜头记下来作为对标片，以后同类镜头照着它验收。
