# 开局

人和设计负责人一起搭起双角色工作方式（Matt 的技能、DispatchDock、执行技能 `run-spec`）的步骤，有两条路径：

- **新仓库**：从第 0 步开始照做。来自本仓库建仓的复盘，证据和数据见 `docs/reports/bootstrap-retro.md`。
- **已有仓库**（目标仓库已经在开发）：同样走这些步骤，另按「已有仓库」一节补做。来自第一次迁移（design-system），记录见 `docs/research/run-spec-migration.md`。

每一步写明谁做、做到什么算完。标【初始化】的是机械步骤，适合以后交给迁移初始化技能。

## 分工

- **人**：只有人能做的，以及要人拍板的。建仓、装技能、运行只能手动调用的技能、登录和权限、目标、范围和取舍。
- **设计负责人**：探查、读参考、提方案、写规则、落地、实测。
- **环境事实**（能不能联网、有没有 GPU、装了什么）用实测回答，谁方便谁去测。

## 0. 人：开口前的准备

- 用日常工作的系统用户建仓，名字一开始就定成最终的：本地目录、包名、远程仓库三者一致。Claude Code 按路径存会话记录，中途改名会让记录分散在两个目录里。
- 装好要用的技能：领域技能，加上 Matt 的技能（先装全，去留在对齐时再定）。DispatchDock 克隆进参考目录，安装留到落地那一步。
- 参考资料放进一个只读、不进 git 的目录。
- 确认 Codex 能运行、`gh` 已登录。
- 第一条消息写清：角色、背景、长期目标（这个仓库以后要承担什么，不只是眼前这件事）、材料在哪、请先读和拆解。

完成标准：第一条消息发出后，设计负责人开工不需要再向人要材料。

## 1. 设计负责人：探查环境【初始化】

逐项实测，结果整理成一张环境事实表给人看：

- **git**：命令能否运行（属主不对会报 dubious ownership）、提交身份、远程仓库。
- **基线**：包管理器和锁文件是否一致；用派发 Codex 的那个系统用户实际跑一遍验证命令（浏览器这类依赖可能只装在别的用户名下）；最近几次 CI 有没有间歇性失败。
- **版本**：Node、`gh`（建 sub-issue 要 2.83 以上）、Codex。
- **Codex**：沙箱内和授权后分别测联网；`.agents/skills/` 下的技能它都能看到，列出来。
- **技能**：互相调用的依赖是否装齐，哪些设了只能由人手动调用。
- **硬件**：任务要用的硬件（例如 GPU）按平台的实际位置查。WSL 的 `nvidia-smi` 在 `/usr/lib/wsl/lib`，不在 PATH 里。

完成标准：表里每一项都是命令的实际输出；查不到的写"未知"。

## 2. 设计负责人：读参考

- 读参考项目的文档和脚本，以及领域材料，写成 `docs/research/` 下的文档，每条注明是出处、实测还是推断。
- 要看大量图片、视频或长输出的拆解，交给子代理或单独的会话，主会话只读写好的文档。本仓库在主会话里读了 27 张图，上下文到 25 万，后面每次调用都在重读。

完成标准：研究文档写完，主会话里只留它们的摘要。

## 3. 一起对齐

设计负责人每轮回复的结构：结论 → 理由 → 要你决定的事，每件带推荐。人只回不同意的地方，事实问题去实测。开局要定的事和本仓库的选择：

| 事项 | 本仓库的选择 | 写在哪 |
|---|---|---|
| 长期目标 | 做视频、探索 DispatchDock、复利 | `docs/roadmap.md` |
| 仓库形态，方法层和产物层怎么分 | 工作室仓库，依赖只从产物层指向方法层 | `AGENTS.md`「目录与归属」、`docs/workflow/README.md`「以后拆分」 |
| 技能怎么配合，留哪些 | Matt 负责想清楚和拆工单，DispatchDock 负责派发，领域技能两边都用 | `docs/workflow/README.md` |
| 角色怎么不混淆 | 派发时说明角色、`AGENTS.md` 写规则、角色文档列技能权限；DispatchDock 只装给设计负责人 | `AGENTS.md`「角色」、`docs/roles/` |
| 工单放哪 | GitHub Issues，只存一份，按 issue 号派发 | `docs/agents/issue-tracker.md` |
| Codex 权限 | 完全权限 | `docs/agents/run-spec.md` |
| 提交格式 | 类型、范围、正文，尾注 `Refs`、`Role` | `AGENTS.md` |
| 什么不进 git | 媒体、参考资料、第三方技能、派发记录 | `.gitignore` |
| 远程仓库的名字和可见性 | `video-studio`，私有 | — |

- 参考项目里的约定（提交格式、注释要求、目录结构）逐条判断适不适合这个仓库，适合再用。本仓库照搬了 DispatchDock 的"一句中文"提交格式，后来因为丢信息改掉了。
- 没经过人确认的建议，写进文档时标"待定"。

完成标准：上表每一项都有结论，并且记得是人定的还是按推荐。

## 4. 人：初始化 Matt 的技能

- 按对齐结果删掉不用的技能。
- 运行 `/setup-matt-pocock-skills`，工单选 GitHub。它会写 `AGENTS.md` 的「Agent skills」一节、`CLAUDE.md` 和 `docs/agents/` 下三份文档。`CLAUDE.md` 只保留一行 `@AGENTS.md`，共同规则都写在 `AGENTS.md`，因为 Codex 只读它。

完成标准：`docs/agents/issue-tracker.md` 已生成。

## 5. 设计负责人：落地

每一项做完就验证、提交：

1. **基线**【初始化】：统一包管理器，修到验证命令通过，补好 `.gitignore`。
2. **远程**【初始化】：推送前检查要上传的文件里没有媒体和密钥；建远程仓库，建分诊标签和执行角色标签。
3. **规则**：先加载 `writing-for-agents`，再按 `dual-role-workflow` 写 `AGENTS.md`、两份角色文档、工作流总图和工单约定。
4. **DispatchDock**【初始化】：固定版本，只装到 `.claude/skills/`。安装命令见 `docs/research/dispatchdock-notes.md`。
5. **执行技能**【初始化】：按 `docs/agents/run-spec.md`「迁移到别的仓库」安装 `run-spec`。
6. **冒烟测试**【初始化】：派一个只读任务给 Codex，确认五件事：认对角色、守住规则、能用 `gh`、汇报格式齐全、看不到设计负责人的技能。
7. **报备**：结尾单列"我自己定了、你应该知道的几处"，改过的本机全局配置要附撤销方法。

完成标准：验证命令通过，已推送，冒烟测试五项都有证据，报备清单交给了人。

## 6. 设计负责人：写路线图，交接给新会话

**路线图**（`docs/roadmap.md`）是每个新会话的入口。它不会被自动加载，靠人在开场白里点名，例如"你的角色是设计负责人。先读 docs/roadmap.md"；文档地图里也把它标为起点。

内容只放新会话开工要用的四部分：

- **目标**：长期目标，每条一句。
- **已定**：事项、一句话结论、写在哪。决定的全文留在出处，路线图只做索引。
- **进度**：勾选清单，做完的条目附上记录的位置（汇报、复盘）。
- **下一步**：新会话的第一件事，以及还没定的事。

更新：设计负责人在每个阶段（一个 spec、一次复盘）收尾时更新进度和下一步，和收尾的提交一起提交。出处改了，路线图只改指针。

全部完成时：

- **已定**：逐行确认出处写全了，然后删掉这一行。
- **进度**：删掉已完成的条目。记录在汇报里，旧版本在 git 历史里（`git log -p -- docs/roadmap.md`），不用另存副本。
- **仓库还要继续**：写上下一阶段的目标和下一步，文件留着，开场白不变。
- **仓库不再继续**：只留一段状态说明，指向最终的汇报；或者删掉文件，同时改掉文档地图和开场白里指向它的地方。

交接前：

- 检查新会话会读到的文档（路线图、文档地图）：给人用的评估清单移出仓库；"遇到某情况就改技能"这类指令改成"记下来告诉用户"；没确认过的建议标"待定"。
- 给人一份逐步的输入指南：每一步输入什么、会看到什么、要做什么。

完成标准：路线图四部分齐全；人照着指南，能在新会话里直接开始彩排。

## 7. 彩排

- 在新会话里用第一个 spec 把流程完整走一遍。题目选这个仓库本来就要做的工程活，本仓库选的是护栏与验收工具。
- 执行流程开局只写能跑通的最小版本，彩排后用 `/retro` 修改。本仓库建仓时写的执行技能，第一次使用后就整体重写了；规则文档基本没变。

## 已有仓库

目标仓库已经在开发时，在上面各步之外补做下面这些。动手之前，设计负责人先把要走的步骤讲给人听，人确认后再开始。

- **第 0 步**：人确认目标仓库已装好 Matt 的技能并跑过 `/setup-matt-pocock-skills`，说明为什么迁、迁完先做什么。
- **第 1 步，读懂目标仓库**：方案或设计文档、术语表、ADR、进行中 spec 的全文都要读完。迁移会改规则文档，没读完就会和已定的决定冲突。design-system 里出过两处：把排法划给了工程负责人，而方案和 spec 规定排法属于体系本身、由裁判判断；把命令手册移出了 `AGENTS.md`，而 spec 的一条用户故事要求它写在那里。
- **第 1 步，多查几项**【初始化】：
  - 长期分支和没合回 `main` 的提交、PR 的用法、GitHub 允许的合并方式；
  - 第三方技能是否进了 git、本地有没有改动（`git status`、锁文件里的哈希）、和来源仓库的技能差几个；
  - 现有 `.gitignore` 里要软链接进 worktree 的目录，是否写成了带斜杠的形式。
- **第 3 步，多定几件事**：迁移时机（进行中的 spec 做完再迁，还是现在迁）；已有规则文档里哪些留下、哪些移到按需读的文档；目标仓库产品里的角色和"用户"一类词，怎样和开发协作的说法区分；第三方技能是否和来源仓库保持一致。目标仓库已有的命名和结构（文件名、目录）要改，先问人。
- **检查点**：落地之前，把长期分支开 PR 合回 `main`，由人合并，并把合并方式锁成只用 merge commit。之后每个 spec 从 `main` 开 `spec/<号>-<短名>`。
- **第 5 步**：
  - 在已有的 `AGENTS.md` 上改：`/setup-matt-pocock-skills` 生成的「Agent skills」一节原样保留，加上角色、提交格式、目录与归属；每轮都加载、却只在某些时候用到的内容（例如命令手册）移到按需读的文档，`AGENTS.md` 留一句指针。
  - 第三方技能已经进了 git 的，用 `git rm -r --cached` 退出跟踪，核对暂存区后不带路径提交。只提交指定路径时，git 会按磁盘上的现状提交，把这些文件重新加回去。
- **第 6 步**：在进行中的 spec 下留言，说明流程变了、接下来从哪个分支继续。
- **之后**：迁移中碰到的问题记回来源仓库，作为初始化技能的输入。

## 交给初始化技能的范围

- **可以交给它**：标【初始化】的步骤，都是能用命令完成、结果能机械检查的。
- **只能提示人去做**：第 0 步和第 4 步。`/setup-matt-pocock-skills` 只能由人手动运行，初始化技能要在对的时候提醒人。
- **留在对话里**：第 2、3、6、7 步，都要判断。
