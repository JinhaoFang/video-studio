# 已经在开发的仓库多查的项目

每一项都来自第一次手工迁移（design-system）碰到的问题。

- **设计文档读完再提建议**：方案或设计文档、术语表、ADR、进行中 spec 的全文。规则文档的修改会和已定的决定冲突，例如把属于产品本身的设计工作划给了工程负责人。
- **长期分支**：有没有比 `main` 多很多提交、从没开过 PR 的分支。`run-spec` 按 `spec/<号>-` 找集成分支；有长期分支时，建议先开 PR 合回 `main` 作为检查点，之后每个 spec 从 `main` 开分支。
- **第三方技能进了 git**：`git ls-files .agents .claude/skills`。进了的，建议用 `git rm -r --cached` 退出跟踪，核对暂存区后不带路径提交。提醒用户：退出跟踪以后，在主工作区切到还跟踪着它们的旧提交再切回来，这些技能会从磁盘上消失，看旧历史用 `git show` 或另开 worktree。这个 PR 合并后更新本地 `main` 也一样：先 `git fetch origin main:main`，再切过去；先切到还停在旧提交的本地 `main` 再拉取，就会碰上。
- **第三方技能有本地改动**：它们不进 git，`git status` 看不到；锁文件里的哈希由安装工具计算，没法重算比对。从来源把同名技能重新装一份到临时目录（例如在临时的空仓库里运行 `npx skills add <来源> --skill <技能名> -a codex -y`），再和本仓库的逐文件比对。改动会改变 Codex 能自己调用的范围（例如把只能手动运行的技能改成可由模型调用），有就问用户怎么处理。
- **产品里也有"角色""用户"**：术语表里的产品角色和开发协作的设计负责人、工程负责人是两套东西。问清对应关系，写进 `AGENTS.md` 的角色一节。
- **`.agents/skills/` 里会不会有本仓库自己的技能**：软链接进 worktree 的粒度只到目录；以后要在那里放自己进 git 的技能，就和整目录软链接冲突，记进路线图的待定项。
- **已有规则文档的结构**：每轮都加载、却只在某些时候用到的内容（例如命令手册）建议移到按需读的文档，`AGENTS.md` 留一句指针；`/setup-matt-pocock-skills` 写的「Agent skills」一节原样保留。
