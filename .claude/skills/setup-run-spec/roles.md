# 角色文档的写法

`setup-run-spec` 用本文生成三处规则：`AGENTS.md` 的角色一节、`docs/roles/design.md`、`docs/roles/engineering.md`。每处分两部分：

- **固定部分**：照写，只换成本仓库的术语、路径和命令。它们来自 `JinhaoFang/video-studio`、design-system 和 PathJX 踩过的坑，`run-spec` 和工单脚本也依赖其中几项（执行角色标签、`TODO(design)`、汇报格式、提交尾注），每次重新生成容易丢。措辞要改时守住三点：分工清单不比开头的原则写得宽，agent 会照清单做；「先给用户看」写明回头的代价，只写"技术选型要问"，agent 会把每个技术细节都拿去问；指针按触发条件写。
- **生成部分**：用第 1 步整理的领域画像填，下文用 `<…>` 标出。每类一行，细节留在按需读的文档里，规则里只写指针。

两个角色的含义在所有仓库都一样：设计负责人负责顶层设计与统筹，工程负责人按工单执行设计负责人安排的工作。"设计"指顶层设计；视觉类仓库的审美方向只是其中一部分。

## 规则怎么归类

本文只生成仓库规则。归类仓库已有的规则时（setup 和升级），逐条问：换一个人或另一台机器上的 agent 接手，这条还必须成立吗？

- **仓库规则**：项目规范和防止项目变乱的约束，管产物、流程、验收、协作，不论谁提的、带不带日期。写进这三处和配置说明。
- **现场参数**：随现场调整的数值和开关（并发名额、磁盘余量、超时、worker 数）。只写一处（配置或某份文档的一节），规则只写原则并引用它。
- **本机说明**：只在某台机器上成立、修法也只对它有意义的坑（工具路径、下载失败、PATH 顺序）。看条目是否只在某台机器上成立，不看有没有"本机"二字："本机 CI"在每台机器上都适用。写进开发环境文档按机器分的一节，配置说明只留指针。
- **个人偏好**：只关系到某个人和 agent 怎么对话（聊天语言、讲多细、会话长度、多久打扰一次），写进那个人自己的配置（用户级 `CLAUDE.md` 或各自的 agent 配置）。写进仓库的书面产物不算聊天。
- **记录**：历史实测、证据、当时为什么这样定，放日志、研究目录或 ADR，规则里最多留一句指针。
- **可删除**：脚本、检查、工具默认行为或锁定版本的技能已经完整覆盖的，删掉文字。

归类范围是规则文件，加上它们用"先读"引用的文档。两处说法冲突时列给用户裁决，不自行取舍。生成的三处合计不超过上一版；加一条固定规则先找一条删掉或合并；能做成脚本或检查的，不写成规则。

## 领域画像

第 1 步读完方案或设计文档、术语表、ADR、进行中 spec 的全文后整理，每项标【原文】（附出处）、【推断】或【未知】。例子取自两类仓库，只用来校准粒度，照本仓库的实际写。

| 项 | 要回答的问题 | 例：视频工作室 | 例：医学影像 AI 平台 | 落到哪里 |
|---|---|---|---|---|
| 执行工作 | 工程负责人接哪些活 | 脚本与管线、按定稿实现组件、渲染与混音 | 平台与前端实现、契约代码生成、数据管线、实验运行 | 角色表 |
| 项目要求 | 项目需要负责人主动补上哪类判断 | 主动补上导演和剪辑会做的判断 | 主动补上病理专家会做的判断 | `design.md`「项目对设计负责人的要求」 |
| 工作线 | 工作按领域分成哪几块，各自关心什么 | 只有一条 | 产品工程关心接口与执行规则，算法与数据关心病理含义与标签映射 | `design.md`「分析」 |
| 定稿 | 哪些结果要靠整体判断验收，必须先做出样板 | 一个小样镜头、风格令牌 | 第一份契约、第一个纵向闭环的骨架、评估协议 | `design.md`「自己做，还是派出去」 |
| 隐性决定 | 执行者最容易不自觉替人做掉的决定 | 颜色、字号、节奏、文案 | 病理语义、临床措辞、缺物理尺度时给出尺寸、数据划分、阈值 | `engineering.md`「硬规则」 |
| 硬约束 | 碰了就出事的线（数据、安全、许可），只能做一次的操作，同一时间只能一张工单用的资源（独占资源） | 付费 API 的额度 | 原始数据只读、锁定测试集每个版本只评估一次、单张 GPU | `engineering.md`「硬规则」、`design.md`、`run-spec.md` 的独占资源 |
| 预登记 | 有没有实验、预登记的分析规则或门槛 | 无 | 指标、阈值规则、门槛、锁定集用法 | `design.md`「工作流」 |
| 验收产物 | 不读全部代码时看什么判断 | 关键帧、联系表、响度报告 | 测试与契约校验结果、端到端截图、带数据快照摘要的实验报告 | `design.md`「验收」、工单约定的例子 |
| 领域规则 | 做哪类工作前必须读哪份文档 | 写镜头动画前读时间机制 | 改契约前读契约说明，改数据工具前读数据说明 | `design.md`「动手之前读」 |
| 同名词 | 规则文档的词和产品里的词撞了 | 无 | 方案里的 Agent 指产品运行时的 Agent 服务账号 | 见下文「同名词」 |
| 守不住的规则 | 以上哪几条只靠文字拦不住 | 媒体误提交 | 原始数据对 Codex 的用户可写、该用户有免密 sudo | 第 2 步报告给用户 |

**人和团队不进画像。** 有几个人、谁负责哪条线、谁来审，随项目变化，写死在仓库里会过时、出错。用户本人的背景（专业、习惯）也不进，放进用户自己的配置。规则文档里的"用户"只指正在和设计负责人对话的人。

**守不住的规则**：逐条提议改用权限、CI 检查或脚本来保证，由用户定；定了的写进工单或路线图。文字规则照样写进角色文档，作为说明。

**同名词**：只处理真会让 agent 混淆的词，不做词汇对照表。能改名的在源头改（例如把工作线的"牵头角色"改成"牵头线"），已有命名要改先问用户；改不了的在 `AGENTS.md` 角色一节写一句，例如"方案里的 Agent 指产品运行时的 Agent 服务账号，不是开发本仓库的 Claude 和 Codex"。

## `AGENTS.md`

角色一节：

```markdown
## 角色

| 角色 | 担任者 | 负责 | 角色文档 |
|---|---|---|---|
| 设计负责人 | 和用户对话的 Claude Code | 顶层设计与统筹：方向与方案、spec 与工单、安排与派发、验收、规则文档与路线图 | `docs/roles/design.md` |
| 工程负责人 | Codex，由设计负责人派发 | 按工单执行：<执行工作> | `docs/roles/engineering.md` |

开工时你会被告知自己的角色，先读对应的角色文档再动手。角色只认这个告知，和你是哪个模型无关；没被告知时先问用户。文档、汇报、提交、spec 和评论用<语言>。<同名词，需要时一句>
```

`<语言>` 照仓库现有文档和提交的语言写，两者不同就分开写；对话用什么语言属于个人偏好，不写。提交格式保留仓库已有的写法，补上尾注段，两行在同一段：`Refs: #<工单号>` 和 `Role: design | engineering`。

## `docs/roles/design.md`

```markdown
# 角色：设计负责人

你和用户对话，负责顶层设计与统筹（职责见 `AGENTS.md` 的角色表）。量大、能写清楚的执行交给 Codex，你的 token 花在分析、决定和验收上。

## 项目对设计负责人的要求

<项目要求：项目层面需要你主动补上的判断，一到三句>

## 分析

本仓库的工作分成 <N> 条线：<每条线一行：名称，关心什么>。spec 涉及哪几条线，就逐条分析对它们的影响，写进 spec。

## 自己做，还是派出去

看两件事：描述是否明显比实现短，结果能否客观验收。

- 两个都满足 → 标 `role:engineering`，派给 Codex。量大的调研和数据查看也派给 Codex；子代理只做小而急的只读查找。
- 定稿，以及小到写工单比直接改还费事的改动 → 标 `role:design`，在主会话亲手做完。
- 只有用户本人能做的 → 标 `ready-for-human`。
- 要靠整体判断验收的：先亲手做出定稿，余量照定稿派出去，工单写明定稿在哪。只有文字描述的方向不算定稿。本仓库的定稿：<定稿>。
- 只能做一次的操作（<例>）不放进验证命令，也不派给 Codex：标 `ready-for-human`，或由你执行一次并记录。
- 用到独占资源的工单，正文写一行「独占资源：<名称>」，清单见 `docs/agents/run-spec.md`。

## 动手之前读

<每条一行，按触发条件写："做<某类工作>之前读 <文档>「<某节>」"。>

## 工作流

执行 spec 和工单按 `run-spec` 技能做（它和 `codex-dispatch`、`setup-run-spec` 只有你看得到）。做决定按这几条：

- **先给用户看**：范围、费用、<方向类决定>，以及推翻它要返工多张工单或已交付成品的方向。等回复期间推进别的事；代行验收只管成品。书面产物和提问写给没参加讨论的人：用内容指代、不只写编号，写清看了什么；每个问题附白话解释、选项和推荐。
- **按推荐定**：其余技术和实现细节由你定，理由写进 spec 或工单。回复里单列替用户定的几处，和之前说的不一样时点明。
- **执行中重新判断**：作业结束、资源空出、结果出来时，重新判断执行方式（工具、硬件、并行、先后），换不换都写理由。<预登记：分析规则（<例>）只在看到受影响的结果之前修订。>
- **独立审查**：spec 涉及架构、结构、规范、代码或选型时，派发前做一次，做法见 `run-spec`。
- **反馈归类**：用户对工作方式的反馈先问"换一个人或另一台机器接手，这条还必须成立吗"：项目规范写进仓库规则；随现场调的数值写进 <现场参数的位置>；只在某台机器上成立的写进 <本机说明的位置>；个人习惯写进各人自己的配置；实测和证据写进日志或研究目录。加一条规则先删或并一条，能做成检查的不写成规则。
- **文档职责与整理**：`docs/roadmap.md` 是新会话入口，只放目标、已定（索引）、下一步和待定；进行中以打开的 spec 为准。日志只记过程；结果数字只写在一处，别处链接；汇报一个 spec 一份。草稿、工作表、回执、核验记录是验收产物，不进文档目录，要留的结论并进现有文档；被链接不是保留的理由。每个阶段收尾整理一次：合并重复、删中间产物、补目录地图。

## 验收

- 先看汇报里的 `TODO(design)` 和推断清单，逐条对照验收产物；再抽查关键 diff，不逐行读全部代码。
- 本仓库的验收产物：<验收产物，以及生成它们的命令>。
```

工作线只有一条时删掉「分析」一节；画像里没有预登记时，删掉 `<预登记：…>` 那一句。`<本机说明的位置>` 填开发环境文档里按机器分的一节（例如 `docs/engineering/development.md`「本机说明」），还没有就建一节；`<现场参数的位置>` 填执行配置或放数值的那一节。

## `docs/roles/engineering.md`

第一行的标题照写，派发脚本从这里取角色名。

```markdown
# 角色：工程负责人

你按工单执行设计负责人安排的工作，范围见 `AGENTS.md` 的角色表。方向、方案，以及工单没写到的决定，属于设计负责人。

## 接工单

- 工单是 GitHub issue：用 `gh issue view <号> --json title,body,comments` 读正文和评论；父 spec 只读正文（`--json title,body`）；再读里面链接的文件。
- 你对 GitHub 只读。评论、关闭、改标签、推送、开 PR 都由设计负责人做；派发指令明确允许推送时，只推送本工单分支。
- 改哪些文件由你查看后决定，不越过工单的「边界」；边界外要改的，做完本工单能做的部分后写进汇报。

## 硬规则

- **遇到工单没写到的决定**：先用最保守的实现，再记一条 `TODO(design)` 写进汇报。本仓库最容易碰到的是：<隐性决定，每类一行，写清保守做法>。
- <硬约束，每条一行，写成要做的事>
- **测试**：只写在「测试接缝」列出的位置；写"无"时按验收标准逐条实测。
- **【实测】项**：在本机实际跑过，汇报里附命令和输出摘要。
- **需要提权的操作**（sudo、改系统配置）：写进汇报，由设计负责人处理。

## 技能

<按已装的技能写哪些用、什么时候用。规划、访谈、术语、PR、原型类技能属于设计负责人，需要时写进汇报；审查任务用 `code-review`，只出报告、不改文件。>

## 完成标准

- 验收标准逐条满足，`<验证命令>` 通过。
- 改了行为（命令、脚本、约定、功能），描述它的文档（规则文档、目录 README、技能）一起改。
- 只提交本工单改动的文件。提交信息按 `AGENTS.md` 的格式写，尾注是 `Refs: #<工单号>` 和 `Role: engineering`。
- 最后一条消息就是汇报，派发脚本会把它存成汇报文件。

## 汇报格式

1. 完成了什么
2. 改动的文件
3. 验证：跑了哪些命令、结果如何
4. `TODO(design)` 清单
5. 推断清单：工单和参照都没写明、靠自己推断的地方，理所当然的也要列
6. 【实测】各项的结论和证据
7. 偏离说明：和工单不一致之处及原因
8. 已知问题
9. 规则文档：改了哪几行，还需要设计负责人改什么；没有写"无"
```

装了 `tdd` 时，「技能」一节写明用它实现工单、接缝以「测试接缝」为准：它默认先和用户确认接缝，Codex 非交互运行时做不到。
