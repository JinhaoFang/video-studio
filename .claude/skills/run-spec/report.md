# spec 汇报的写法

汇报是设计负责人向用户汇报工作：这次做了什么、做成了什么、花了多少、遇到什么、接下来做什么。它不是交给用户检查的中间产物。下面是默认内容，按每次的情况取舍。

## 形式

- 单个 HTML 文件，存进汇报目录，文件名 `spec-<S>-<英文短名>.html`。从模板 [report-template.html](report-template.html) 起步：复制它，换掉数据数组和文字；模板文件头写了怎么换数据、怎么画新的流程图。
- 图优先，给人读：
  - 时间（派发、返工、审查的先后和并行）用时间线；
  - 用量和数量的对比（Claude 与 Codex、本次与上次、审查发现按处理方式）用条形图，随时间变化的量用折线；
  - 结构和数据流（流程改了什么、模块怎么连）用结构图或流程图。
  - 表格只留给要逐项查找的清单，例如每张工单的提交号。大段文字改成短句。
- 关键数字、图表的数值和坐标范围都从页面里的一份数据数组算出来，不手写：PR 审查后返工时要往里补数据。
- 只用系统字体，不引任何外部资源；脚本整体放在一个块里，只用 `const`、`let` 和箭头函数，不新增全局变量：非严格模式下块里的 `function` 声明也会挂到全局，全局名字和浏览器自带的 `window.top` 这类重名时整页空白。
- 深浅色都要可读，手机宽度下不横向滚动；图表要有文字标注，不能只靠颜色区分。
- 交付前用无头浏览器打开一次：控制台零报错，比较页面和空白页的 `Object.keys(window)` 没有多出来的名字，再看一眼浅色、深色和手机宽度的截图。
- 交给用户：给出文件路径。不发布到 claude.ai 或其他外部服务。

## 要有

- **任务**：目标、范围、一句话结果（含 PR 和 CI 的状态）。
- **交付**：交付了什么，对用户意味着什么。
- **时间线**：派发、返工、审查和关键节点。
- **成本与效率**：派发次数、每次和合计的执行时间、token 用量（Codex 的输入、其中缓存、输出；设计负责人主会话和子代理的用量）、并行度、返工次数。写出两个比值：设计负责人主会话与 Codex 的用量比，主会话每次回复的平均上下文。数据缺失时写明原因。
- **质量**：测试数、CI、关键的实测数据、审查发现了多少、怎么处理的。
- **决定**：谁做了哪些决定。
- **问题与处理**：包括设计负责人自己的失误。
- **流程发现、遗留与下一步**。

## 不放

原始日志、git log、diff、评论全文。需要时给 issue 或 PR 的链接。细节只在影响判断时放，比如一次异常长的派发、一次返工的原因。

## 数据从哪里取

- **Codex**：工单验收评论里的派发数据，按批审查的用量在 spec 的审查评论里。缺的从 `~/.codex/sessions/` 下的会话记录补：最后一个 `token_count` 事件里的 `total_token_usage`，`session_meta` 里的 `cwd` 对应是哪个 worktree。worktree 删掉后这些记录还在。
- **设计负责人主会话**：`~/.claude/projects/<项目目录>/<会话>.jsonl` 里每条回复的 `message.usage`。按 `message.id` 去重，跳过 `isSidechain` 的记录。平均上下文是每条回复的输入、缓存读取和缓存写入之和的平均。
- **子代理**：任务通知里的 `subagent_tokens`。
- **`review-spec` 和 `watch`**：`claude -p` 的用量在它们的输出文件和日志里。
