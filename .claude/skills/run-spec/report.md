# spec 汇报的写法

汇报给用户读：先说交付了什么、目标达到没有，再讲过程、成本和问题。

## 形式

- 单个 HTML 文件，存进汇报目录，文件名 `spec-<S>-<英文短名>.html`。复制模板 [report-template.html](report-template.html)，换掉数据和文字。
- 表格用于逐项查找的清单；图只用在比文字和表格更清楚的地方：派发时间线、目标的改前改后、Claude 与 Codex 的用量对比、领域结果。结构图只在 spec 改了结构或流程时画。
- 不放：和以前 spec 的用量对比、累计输出折线、按处理方式分组的发现图、每次都一样的分工流程图。
- 数字和图都从页面里的一份数据算出来，返工后补数据即可。
- 只用系统字体，不引外部资源；脚本整体放在一个块里，只用 `const`、`let` 和箭头函数，不新增全局名字（重名 `window.top` 这类自带名字会整页空白）。
- 深浅色可读，手机宽度不横向滚动，图有文字标注。交付前用无头浏览器打开：控制台零报错，页面和空白页的 `Object.keys(window)` 相比没有多出来的名字，看浅色、深色、手机宽度三张截图。不发布到外部服务。

## 节次

1. **标题与关键数字**：日期、spec、PR 一行；4～6 张数字卡片（工单、派发、测试、目标达成数、用时）。
2. **任务**：目标、范围、一句话结果（PR、CI 状态）。限制放提示框。
3. **交付**：表，交付、工单、对用户的意义。
4. **目标核对**：spec 问题陈述里的现状按同一口径重测，每项一条 `goal`（改前、改后、单位、方法、结论、证据）；同单位的数字画对比条，其余列表。没达到的写原因和去向。
5. **领域结果**（可选）：实测、选型、性能等，用最能说明问题的图或表。
6. **时间线**：关键节点表，加派发甘特图。每条写类别（首次、返工、审查、长作业、设计工单）、起止、分钟、状态，可按日期筛选。
7. **成本与效率**：用量表（Codex 工程派发、按批审查、设计负责人主会话、独立审查、子代理：用时、输入、其中缓存、输出）；主会话有几种口径（例如整个会话、spec 创建之后）就列几行，对比只用标了 `compare` 的一条；Claude 与 Codex 的对比条；两个比值：主会话与 Codex 的用量比、主会话每次回复的平均上下文。派发明细折叠。只报这次的数。
8. **质量**：测试数、CI（附运行链接）、关键实测；审查表（审查、状态、发现数、取舍）和发现表（发现、来源、处理、状态）。
9. **决定**：表，谁、决定与理由；用户的和设计负责人的分开。
10. **问题与处理**：表，问题与责任、影响与处理；设计负责人自己的失误照写。
11. **流程发现、遗留与下一步**。
12. **数据口径与缺项**：表。缺的写"未知"，不估算、不按零算。
13. **页脚**：数据截点、来源。

原始日志、diff、评论全文不放，给链接。证据链接指向 GitHub（验收评论、审查评论、PR），不指向本机验收产物：`cleanup` 之后它们就不在了。要引用的收尾证据（目标核对、最终验证）先评论到 spec 上再链接。

## 数据从哪里取

- **Codex**：工单验收评论和 spec 的审查评论。缺的从 `~/.codex/sessions/` 补：最后一个 `token_count` 事件的 `total_token_usage`，`session_meta.cwd` 对应 worktree，worktree 删掉后仍在。
- **设计负责人主会话**：`~/.claude/projects/<项目目录>/<会话>.jsonl` 每条回复的 `message.usage`，按 `message.id` 去重，跳过 `isSidechain`。平均上下文是每条回复输入、缓存读取、缓存写入之和的平均。
- **子代理**：任务通知里的 `subagent_tokens`。
- **`review-spec` 和 `watch`**：`claude -p` 的用量在它们的输出文件和日志里。
